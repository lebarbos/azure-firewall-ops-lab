Azure Firewall — laboratório de operação

Guia autocontido para operar, testar e diagnosticar Azure Firewall em uma topologia didática com secured vWAN, firewall N-S e logs estruturados.

Início

⏱ 20 min para boas-vindas, preflight e disparo do deploy

Custo e cleanup são parte do exercício

Este lab cria dois Azure Firewalls Premium, um secured Virtual Hub, Bastion e duas VMs. Você deve executar o cleanup verificado no fim da sessão.

O que é o lab e para quem

O que: um laboratório prático para operar, testar e diagnosticar Azure Firewall em uma topologia com tráfego E-W e N-S separados.

Por que: o objetivo não é decorar telas do Portal. Você vai prever qual política decide um fluxo, alterar a configuração com segurança e provar a decisão por rota, teste e KQL.

Você vai aprender

  • Diferenciar tráfego E-W, saída N-S e administração via Bastion.
  • Explicar a ordem real de processamento: pai antes da filha; DNAT, Network e Application; RCG e RC por prioridade.
  • Usar IP Groups, diagnostic settings resource-specific, workbook e consultas KQL para responder por que um fluxo passou ou falhou.
  • Tratar propagação de policy como parte da operação, não como detalhe.
CLI

Sem equivalente direto no CLI: esta é uma orientação conceitual para a sessão.

Verifique: você entende que o lab é individual, temporário e não representa uma configuração de produção.

Pré-requisitos

O que: confirme o acesso antes de abrir o Cloud Shell.

Por que: falhas de quota, permissão ou assinatura errada consomem mais tempo que a teoria do lab.

Portal

  1. Use uma assinatura própria ou de treinamento, com permissão Owner ou Contributor suficiente para deployment e recursos de rede.
  2. Abra o Azure Portal em um navegador moderno e confirme que você está no diretório correto.
  3. Abra Cloud Shell › Bash. O roteiro assume Bash, não PowerShell.
  4. Tenha uma senha forte para o usuário labadmin. Você vai digitá-la no script; ela nunca deve ir para arquivo, chat, print ou parâmetro de linha de comando.

Regras do lab

O que: siga estas regras durante todos os exercícios.

Por que: a maior parte dos falsos negativos em Azure Firewall acontece por testar cedo demais, usar senha de forma insegura ou refazer o deploy no momento errado.

Regras operacionais

  • Depois de mudar policy ou rule collection, espere o firewall voltar a Succeeded e aguarde mais 1–2 minutos antes do teste.

  • O lab é cliente-neutro e temporário. Não copie esta topologia como padrão de produção sem revisão de arquitetura.

Atenção ao rótulo

O Portal mostra as rotas do Routing Intent com o tipo Virtual network gateway, não VirtualAppliance. Isso é normal no vWAN: o que identifica o firewall do hub é o IP do próximo salto. Confira em fw-fwlab-ew › Overview que ele é o IP privado do firewall.

CLI

Verifique: se A não alcança B, olhe primeiro as rotas privadas; se A não sai para Internet, olhe a rota default para fw-fwlab-ns.

Os quatro fluxos do lab

O que: cada fluxo tem um caminho e uma pergunta operacional diferente.

Por que: misturar caminhos leva a diagnósticos errados. Um Deny no firewall N-S não explica um RDP via Bastion; uma rota do hub não explica saída para Internet quando a UDR é mais específica para 0/0.

FluxoCaminhoO que observar
E-Wvm-fwlab-a ↔ vm-fwlab-b → hub vhub-fwlab → fw-fwlab-ewRegras Network na policy pol-fwlab-ew e logs em AZFWNetworkRule.
Saída N-SSpoke → UDR rt-fwlab-egress → fw-fwlab-ns → InternetRegras Application/Network na policy pol-fwlab-ns e SNAT pelo firewall.
AdministraçãoNavegador → bas-fwlab → peering → VMBastion funciona sem regra nos firewalls; isso é proposital.
CLI 
Test-NetConnection 10.120.1.4 -Port 3389
Invoke-WebRequest https://learn.microsoft.com -UseBasicParsing -TimeoutSec 15

Verifique: para cada teste você sabe qual firewall, policy e tabela KQL deveria mostrar evidência.

Por que dois firewalls

O que: fw-fwlab-ew ensina tráfego privado no hub; fw-fwlab-ns ensina saída e inspeção N-S.

Por que: secured Virtual Hub é excelente para trânsito privado, enquanto uma VNet N-S separada deixa UDR, Bastion e SNAT visíveis para o aluno.

Trade-off didático

  • O E-W mostra Routing Intent para tráfego privado, sem peering direto entre A e B.
  • O N-S mostra UDR 0/0, SNAT e Application Rules de forma isolada. O DNAT fica para a demonstração do instrutor.
  • O desenho custa mais que um lab mínimo, mas reduz ambiguidade operacional.
CLI

Sem equivalente direto no CLI: esta é uma decisão de arquitetura do lab.

Verifique: ao criar uma regra, você sabe em qual policy ela pertence e qual fluxo ela afeta.

Por que Bastion não passa pelo firewall

O que: o acesso administrativo usa bas-fwlab na VNet N-S e alcança as VMs pelo peering.

Por que: isso mantém uma trilha de recuperação mesmo quando você quebra regras E-W ou N-S. É proposital no lab, não uma recomendação universal de produção.

Ponto de ensino

Se Bastion funciona enquanto ping, RDP A→B ou saída Web falham, isso não contradiz o firewall. São fluxos diferentes.

CLI

Bastion é usado pelo Portal neste lab; os testes CLI dentro da VM aparecem nos exercícios.

Verifique: você não usa sucesso no Bastion como prova de que E-W ou N-S está permitido.

Conceitos

⏱ 25 min · teoria usada durante o deploy

Routing Intent × UDR

O que: o lab usa Routing Intent no hub para tráfego privado e UDR nas spokes para saída 0/0.

Por que: são mecanismos complementares. O Routing Intent do hub injeta rotas privadas para o secured hub; a UDR local da subnet força Internet para fw-fwlab-ns.

Leitura operacional

  • Em vhub-fwlab, a policy PrivateTrafficPolicy aponta Private Traffic para fw-fwlab-ew.
  • Em rt-fwlab-egress, a rota default-to-fw-ns aponta 0.0.0.0/0 para o IP privado de fw-fwlab-ns.
  • disableBgpRoutePropagation=false é intencional: as spokes precisam continuar aprendendo as rotas privadas do hub.
  • Não habilite Internet Routing Intent no hub neste lab; a saída N-S é o ponto de ensino da UDR.
CLI 
az network route-table show \
  --resource-group rg-fwlab \
  --name rt-fwlab-egress \
  --query "{disableBgpRoutePropagation:disableBgpRoutePropagation,routes:routes[].{name:name,prefix:addressPrefix,nextHop:nextHopType}}" \
  --output json

Verifique: rota default para Internet e rotas privadas têm fontes diferentes; não desabilite propagação BGP para "limpar" a tabela.

Processamento de regras

O que: Azure Firewall Policy avalia tipo de regra antes de prioridade numérica global.

Por que: uma regra Network com número menor não vence um DNAT que casou; uma Application Rule só é avaliada quando não houve match em Network para aquele fluxo aplicável.

Regra que casa termina a avaliação

DNAT casado traduz e permite o fluxo sem passar pelas Network Rules. Sem match no fim, o tráfego cai no deny implícito.

CLI

Sem comando único que simule a ordem de avaliação. O lab usa testes e KQL para provar qual regra decidiu cada fluxo.

Verifique: antes do Ex2, você consegue ordenar DNAT, Network e Application sem olhar a prioridade numérica da RCG.

Hierarquia de policies

O que: no Ex3, pol-fwlab-parent vira base policy de pol-fwlab-ew e pol-fwlab-ns.

Por que: policy pai é ferramenta de governança. Ela deve carregar guardrails, não exceções amplas que furam controles específicos das filhas.

Regra conceitualAplicação no lab
Pai primeirorcg-corp no pai pode decidir antes das RCGs das filhas, mesmo com número maior.
NAT não é herdadoRegras DNAT ficam na policy de cada firewall, nunca no pai. Mostrado na demonstração do instrutor.
Threat Intelligence mode é herdadoA filha só pode ficar mais estrita que a base policy.
Mesma região e tier compatívelO pai é Premium e criado na mesma região das filhas.

  --resource-group rg-fwlab \

Verifique: você não coloca Allow amplo no pai sem discutir impacto sobre Deny das filhas.

SNAT e DNAT

O que: a saída N-S do lab usa SNAT. O DNAT, que publica serviços internos no IP público do firewall, não é exercitado no lab: o instrutor mostra em demonstração.

Por que: NAT muda o que cada ponta enxerga. No DNAT, a VM pode ver o IP privado do firewall, não o IP original do cliente.

Como raciocinar

  • Saída: VM → fw-fwlab-ns → Internet. O destino vê o IP público do firewall.
  • Entrada (demo): Internet → IP público do firewall:porta → IP privado da VM:porta, registrada em AZFWNatRule.
  • Um DNAT que casa é permitido pela NAT Rule; não é preciso criar uma Network Allow duplicada.
CLI 
az network public-ip show -g rg-fwlab -n pip-fwlab-fw --query ipAddress -o tsv

Verifique: você sabe qual IP público os sites da Internet enxergam quando uma VM do lab navega: o do firewall N-S.

Propagação de mudanças

O que: mudanças de policy não ficam efetivas instantaneamente no dataplane.

Por que: testar antes de o firewall voltar a Succeeded gera falso diagnóstico. A regra pode estar salva, mas ainda não aplicada ao tráfego.

Ritual antes de testar

  1. Salve a alteração uma vez; evite múltiplos saves concorrentes.
  2. Aguarde o firewall associado voltar a Succeeded.
  3. Aguarde mais 1–2 minutos.
  4. Gere um fluxo novo. Conexões antigas podem não representar a decisão nova.
CLI 
az network firewall show \
  --resource-group rg-fwlab \
  --name fw-fwlab-ns \
  --query "provisioningState" \
  --output tsv

Verifique: você sabe distinguir "regra salva" de "dataplane aplicou".

Logs estruturados × workbook

O que: resource-specific logs alimentam tabelas AZFW*; workbook ajuda a enxergar padrões.

Por que: o workbook mostra o quê aconteceu. O KQL mostra por quê, com Policy, RuleCollectionGroup, RuleCollection e Rule.

FerramentaUse paraLimite

Dentro de cada passada, conta a prioridade do Rule Collection Group e, dentro do RCG, a da Rule Collection. O primeiro match encerra a avaliação.

Antes de começar

O Ex1 precisa estar concluído: IP Groups criados e rcg-baseline na policy pol-fwlab-ns.

Layout que você vai montar

A ideia: os bloqueios ficam no RCG de número melhor (rcg-wl-a, 200) e as liberações no de número pior (rcg-wl-b, 300). Pelo número, os bloqueios deveriam sempre ganhar; os experimentos mostram quando isso não acontece.

Objetivo

5.2 · Criar o alerta de Application Deny

Ex6 · TLS, URL e IDPS (opcional)

⏱ 30–45 min · Checkpoint C6

Exercício opcional

6.1 · Habilitar TLS inspection com certificado auto-gerado

Por que: depois que o firewall intercepta HTTPS, o certificado apresentado ao cliente passa a ser emitido pela CA do firewall. Se a VM não confiar nessa CA, navegador, PowerShell e curl.exe verão erro de certificado.

CLI

Este bloco é autocontido. Ele localiza o Key Vault pelo prefixo do lab e dá ao seu usuário permissão de leitura de certificados. Para isso, detecta o modelo de permissão do Key Vault criado pelo Portal: papel Key Vault Certificate User no modelo RBAC, ou Access Policy no modelo clássico. Em seguida, baixa a CA em DER, converte para base64 e injeta o conteúdo nas duas VMs por Run Command.

RG='rg-fwlab'
KV_NAME=$(az keyvault list -g "$RG" --query "[?starts_with(name, 'fw-cert-kv-')].name | [0]" -o tsv)

if [ -z "$KV_NAME" ]; then
  echo "Key Vault com prefixo fw-cert-kv- não encontrado. Conclua o passo 6.1 primeiro." >&2
else
  ME_OBJECT_ID=$(az ad signed-in-user show --query id -o tsv)
  KV_ID=$(az keyvault show -n "$KV_NAME" --query id -o tsv)

  if [ "$(az keyvault show -n "$KV_NAME" --query properties.enableRbacAuthorization -o tsv)" = "true" ]; then
    echo "Key Vault em modo RBAC: atribuindo 'Key Vault Certificate User' ao seu usuário..."
    az role assignment create \
      --assignee-object-id "$ME_OBJECT_ID" \
      --assignee-principal-type User \
      --role "Key Vault Certificate User" \
      --scope "$KV_ID" \
      -o none
    echo "Aguardando a propagação do RBAC (60 s)..."
    sleep 60
  else
    echo "Key Vault em modo Access Policy: concedendo get/list de certificados..."
    az keyvault set-policy -g "$RG" -n "$KV_NAME" \
      --object-id "$ME_OBJECT_ID" \
      --certificate-permissions get list \
      -o none
  fi

  CERT_NAME=$(az keyvault certificate list --vault-name "$KV_NAME" \
    --query "[?starts_with(name, 'fw-cert-')].name | [0]" -o tsv)
  echo "Certificado: $CERT_NAME"

  az keyvault certificate download \
    --vault-name "$KV_NAME" \
    --name "$CERT_NAME" \
    --file /tmp/lab-tls-ca.cer \
    --encoding DER \
    -o none

  CERT_B64=$(base64 -w 0 /tmp/lab-tls-ca.cer 2>/dev/null || base64 /tmp/lab-tls-ca.cer | tr -d '\n')

  for VM in 'vm-fwlab-a' 'vm-fwlab-b'; do
    echo "Instalando CA em $VM..."
    az vm run-command invoke -g "$RG" -n "$VM" \
      --command-id RunPowerShellScript \
      --scripts "\$bytes = [Convert]::FromBase64String('$CERT_B64'); \$path = 'C:\Windows\Temp\lab-tls-ca.cer'; [IO.File]::WriteAllBytes(\$path, \$bytes); Import-Certificate -FilePath \$path -CertStoreLocation 'Cert:\LocalMachine\Root' | Select-Object Subject, Issuer, Thumbprint" \
      --query "value[0].message" -o tsv
  done
fi

Contributor não basta no modo RBAC

Se o comando az role assignment create falhar com AuthorizationFailed, peça a quem é Owner da assinatura para atribuir o papel, ou baixe o certificado pelo Portal com uma conta que já tenha acesso.

Por que este Run Command usa aspas duplas?

Na maior parte do guia, o PowerShell dentro de --scripts fica entre aspas simples para o Bash não expandir variáveis. Aqui a exceção é proposital: o Bash precisa interpolar $CERT_B64. Por isso, os $ do PowerShell foram escapados como \$.

Troubleshooting

Diagnóstico rápido · preserve evidência antes de corrigir

Regra de ouro

Leia a mensagem completa antes de repetir comandos. Em especial, não reexecute o deploy depois do Ex3 sem entender o impacto: isso pode desfazer o basePolicy das filhas.

Playbook: em que ordem investigar

Quando usar: "o tráfego não passa" ou "está lento", sem pista ainda. Vá do mais barato para o mais caro e pare quando achar a causa.

  1. O serviço está saudável? fw-fwlab-ns › Resource health e a métrica Firewall health state por Status/Reason (Ex5, passo 5.5).
  2. O firewall está lento? Latency Probe e Observed Capacity Units. Lembre: a latência é a do firewall, não a do caminho inteiro.
  3. O pacote chega ao firewall certo? Rotas efetivas da NIC (Arquitetura). Sem rota, não há log.
  4. Qual regra decidiu? KQL nas tabelas de decisão (rastreio multitabela, top denies, rule hits) e o workbook.
  5. A sessão fechou? Flow trace (bônus 2.3): SYN-ACK, FIN, RST, INVALID. Só L3/L4; ligue só durante a investigação.
  6. Quem está consumindo banda? Top flows: mostra as conexões de maior throughput. Consome CPU do firewall; neste lab é demonstrado pelo instrutor, não executado pelo aluno.
  7. Alguém mudou algo? Change tracking no Resource Graph (Ex3, passo 3.6).
  8. Nada explica? Abra chamado com as evidências: horário, origem/destino/porta, rotas efetivas, consultas e métricas.

Deploy falhou

Sintoma: o deployment fica Failed ou um script mostra erro como AuthorizationFailed, AnotherOperationInProgress ou InvalidTemplateDeployment.

Causa provável: permissão insuficiente no escopo de deploy, operação concorrente em recurso de rede, provider ainda não registrado, template inválido ou parâmetro incompatível.

Como confirmar: abra Subscription › Deployments › fwlab-* e leia a mensagem completa da operação com falha, incluindo Details e erro interno. Não use apenas o código resumido.

Como resolver: corrija a causa específica. Para AuthorizationFailed, valide o papel no escopo e se o provider está registrado. Para AnotherOperationInProgress, aguarde a operação concorrente terminar. Para InvalidTemplateDeployment, leia o erro interno de recurso/SKU/quota. Se o deploy falhar antes do Ex1 e a causa for corrigida (por exemplo, numa versão nova do ZIP), rode ./scripts/deploy.sh --force com a mesma senha: o deploy é incremental e só cria o que faltou. Depois do Ex3, não use --force nem rerode a base sem aceitar que o basePolicy pode ser removido.

CLI 
# Use o Portal como fonte principal da mensagem completa.
# Se souber o nome do deployment, consulte o status sem reexecutar:
az deployment sub show --name "<deployment-name>" -o jsonc

Bootstrap da VM falhou

Sintoma: o checkpoint C0 acusa falha na extensão bootstrap, a página IIS não responde dentro da VM ou o marcador LAB_BOOTSTRAP_OK não aparece.

Causa provável: CustomScriptExtension falhou durante instalação do IIS/regras do Windows Firewall, a VM não conseguiu baixar dependências necessárias do agente, ou o caminho de saída pelo firewall N-S ainda não estava pronto.

Como confirmar: confira o instance view da VM e procure a extensão bootstrap. Dentro da VM, leia C:\fwlab\bootstrap.log e verifique se existe C:\fwlab\bootstrap.ok.

Como resolver: preserve o log, confirme se o firewall N-S e a collection de infraestrutura estão em Succeeded, então reavalie a extensão. Se o problema depender de tráfego de plataforma, mantenha a regra de infraestrutura para Blob e registre a causa exata.

CLI 
az vm get-instance-view -g rg-fwlab -n vm-fwlab-a \
  --query "instanceView.extensions[?name=='bootstrap'].{name:name,status:statuses[-1].displayStatus,substatus:substatuses[-1].message}" \
  -o jsonc

az vm run-command invoke -g rg-fwlab -n vm-fwlab-a \
  --command-id RunPowerShellScript \
  --scripts 'Get-Content C:\fwlab\bootstrap.log -Tail 80; Test-Path C:\fwlab\bootstrap.ok' \
  --query "value[0].message" -o tsv

Cloud Shell caiu ou a sessão expirou

Sintoma: o clone sumiu, .lab/env não existe ou os scripts não encontram mais os arquivos do lab.

Causa provável: Cloud Shell é temporário e encerra sessões ociosas; ao recriar a sessão, o que estava fora do diretório persistente pode se perder.

Também acontece: o preflight para com Bicep CLI not found ou com extensão ausente. Repita o passo 0.2 (az bicep install e as extensões) e rode o preflight de novo.

Como confirmar: reabra o Cloud Shell e veja se ~/azure-firewall-ops-lab existe.

Como resolver: reclone e rerode os scripts idempotentes que leem estado do Azure, como o checkpoint. Os recursos no Azure não são afetados pela queda do Cloud Shell. Não use keep-alive para contornar a expiração da sessão.

CLI 
az bicep install
git clone https://github.com/lebarbos/azure-firewall-ops-lab ~/azure-firewall-ops-lab
cd ~/azure-firewall-ops-lab
./scripts/checkpoint.sh C0

Bastion não conecta na VM

Sintoma: o botão Connect via Bastion falha, fica carregando ou a sessão RDP não abre.

Causa provável: Bastion não está Succeeded, peering N-S ↔ spoke não está ativo, a VM não está pronta, ou o Windows Firewall não tem a regra de RDP esperada para a AzureBastionSubnet.

Como confirmar: confira o estado de bas-fwlab, os peerings peer-fwlab-ns-to-a/peer-fwlab-ns-to-b e a regra de firewall do Windows via Run Command.

Como resolver: aguarde Bastion e peerings ficarem prontos; se a VM está acessível por Run Command, restaure a regra de RDP do Windows para 10.130.1.0/26. Bastion Basic suporta conexão a VMs em VNets pareadas; se a conexão ainda falhar, use Run Command como acesso alternativo e registre a evidência.

CLI 
az network bastion show -g rg-fwlab -n bas-fwlab --query "{name:name,state:provisioningState}" -o table
az network vnet peering list -g rg-fwlab --vnet-name vnet-fwlab-ns -o table
az vm run-command invoke -g rg-fwlab -n vm-fwlab-a \
  --command-id RunPowerShellScript \
  --scripts 'Get-NetFirewallRule -DisplayName "*Remote Desktop*" | Select-Object DisplayName,Enabled,Direction,Action' \
  --query "value[0].message" -o tsv

Logs não aparecem

Sintoma: as consultas KQL retornam vazio logo após um teste.

Causa provável: diagnostic setting não foi criado nos dois firewalls, o destino não está em modo Resource specific, a categoria necessária não foi selecionada, a ingestão ainda está atrasada ou o intervalo de tempo da consulta não cobre o teste.

Como confirmar: confira Firewalls › Diagnostic settings nos dois firewalls, valide Dedicated, selecione um intervalo de 30 a 60 minutos e use a consulta de referência tabelas recebendo dados.

Como resolver: corrija o diagnostic setting para law-fwlab, aguarde 5–15 minutos, gere novo tráfego e consulte novamente. Ausência de log não é prova de Allow nem de Deny.

Caso especial, AZFWFlowTrace vazia: confirme que o recurso AFWEnableTcpConnectionLogging está Registered e que a categoria está marcada no diagnostic setting. Se ainda assim continuar vazia, faça uma atualização no firewall (az network firewall update, sem mudar nada) para aplicar o recurso. Application rules nunca aparecem nessa tabela.

CLI

Use o Portal para conferir visualmente as categorias. Para a investigação KQL, use a seção Referência KQL em vez de duplicar a consulta aqui.

Seletor do Key Vault travado em Loading

Sintoma: no Ex6, a tela de TLS inspection fica presa em Loading ao selecionar o Key Vault/certificado.

Causa provável: inconsistência temporária do Portal, permissões de segredo insuficientes para o usuário/managed identity ou recurso auto-gerado ainda propagando.

Como confirmar: confira se o Key Vault fw-cert-kv-* existe, se a managed identity fw-cert-id-* foi criada e se há permissão de Get/List para secrets.

Como resolver: no Portal, alterne TLS inspection para Disabled, clique em Save, volte para Enabled e selecione novamente. Se persistir, valide permissões no Key Vault e registre evidência para ajuste do roteiro.

CLI 
az keyvault list -g rg-fwlab --query "[?starts_with(name, 'fw-cert-kv-')].{name:name,location:location}" -o table

A regra "não funcionou"

Sintoma: logo após salvar uma policy, o teste ainda mostra o comportamento antigo.

Causa provável: a alteração ainda está propagando para o firewall, ou você testou com uma conexão persistente aberta antes da mudança.

Como confirmar: confira o provisioning state do firewall/policy e gere uma conexão nova depois de esperar. Compare o horário do teste com o horário dos logs.

Como resolver: espere o recurso voltar a Succeeded e mais 1–2 minutos antes de testar. Feche o cliente, rode um novo processo e use KQL para provar a regra atual.

CLI 
az network firewall show -g rg-fwlab -n fw-fwlab-ns --query "{name:name,state:provisioningState}" -o table
az network firewall policy show -g rg-fwlab -n pol-fwlab-ns --query "{name:name,state:provisioningState}" -o table

RDP caiu depois de uma mudança

Sintoma: uma sessão RDP A→B aberta cai imediatamente depois de salvar uma regra Deny.

Causa provável: mudar uma regra para negar tráfego previamente permitido derruba sessões existentes correspondentes.

Como confirmar: abra os logs AZFWNetworkRule no horário da queda e procure o Deny de TCP 3389 vindo da policy/RCG esperados.

Como resolver: isso é esperado no Ex3 quando o guardrail é aplicado. Use Bastion para administração, porque Bastion → VM passa pelo peering N-S e não pelo firewall E-W do experimento.

CLI

Use a consulta ex3-guardrail na seção KQL; não duplicamos o bloco aqui para evitar âncoras repetidas.

Redeploy desfez o basePolicy do Ex3

Sintoma: depois de reexecutar o deploy da base, pol-fwlab-ew e pol-fwlab-ns não herdam mais de pol-fwlab-parent.

Causa provável: o deploy base reconcilia as policies filhas para o estado original sem basePolicy.

Como confirmar: confira a propriedade basePolicy.id das duas policies. Se estiver vazia, a hierarquia ativa foi removida.

Como resolver: restaure a associação ao pai com o mesmo caminho do Ex3 e refaça as provas de herança. Não declare C3 concluído com base em logs antigos.

CLI 
PARENT_ID=$(az network firewall policy show -g rg-fwlab -n pol-fwlab-parent --query id -o tsv)
az network firewall policy update -g rg-fwlab -n pol-fwlab-ew --set basePolicy.id="$PARENT_ID"
az network firewall policy update -g rg-fwlab -n pol-fwlab-ns --set basePolicy.id="$PARENT_ID"
