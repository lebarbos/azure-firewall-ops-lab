Ex5 · Alertas de métrica

⏱ 30 min · Checkpoint C5

Objetivo

Você vai sair do modo “olhar o log quando alguém reclama” para o modo “ser avisado quando um sinal operacional importante muda”. Neste exercício, o alerta que dispara usa a métrica {{c.alerts.appDeny.metric}}; o alerta de {{c.alerts.health.metric}} fica configurado para operação.

Um alerta de métrica avalia séries temporais já agregadas pelo Azure Monitor. Um alerta de log avalia uma consulta KQL no Log Analytics. Aqui usamos métrica porque o objetivo é reduzir latência operacional e custo de avaliação: o sinal já existe como métrica de plataforma do Azure Firewall. Use log alert quando você precisar de lógica avançada, junções ou enriquecimento com KQL.

Teste de canal ≠ teste de condição

Test action group prova que o e-mail consegue receber uma notificação de exemplo. Ele não prova que a condição do alerta ficou verdadeira, nem que o alerta entrou em estado Fired. Por isso a prova deste exercício é um disparo real (passos 5.2 e 5.3), que funciona em qualquer assinatura.

5.1 · Criar o Action Group

O que: crie o Action Group {{c.names.ag}}, com nome curto {{c.names.agShort}}, e adicione o e-mail do aluno.

Por que: o Action Group separa o canal de notificação da regra de alerta. Assim, vários alertas podem reutilizar o mesmo destino de e-mail, webhook ou automação.

O Display name (até 12 caracteres) é o que aparece no assunto do e-mail. O common alert schema entrega o mesmo formato de payload para qualquer tipo de alerta, o que facilita ler o e-mail e, depois, ligar um webhook.

Portal

  1. Crie o grupo. Abra Monitor › Alerts › Action groups e clique em + Create. Na aba Basics, preencha:
    • Resource group: {{c.names.rg}}
    • Region: Global (padrão)
    • Action group name: {{c.names.ag}}
    • Display name: {{c.names.agShort}}
  2. Adicione o e-mail. Clique em Next: Notifications e, em Notification type, escolha Email/SMS message/Push/Voice. No painel lateral:
    • Email: marcado, com o seu e-mail no lugar de voce@exemplo.com
    • Enable the common alert schema: Yes
    Clique em OK e, na coluna Name, use aluno.
  3. Pule as abas Actions e Tags. Clique em Review + create › Create e espere a implantação terminar.
  4. Teste o canal (opcional, só em assinatura paga). Abra Monitor › Alerts › Action groups › {{c.names.ag}} e clique em Test:
    • Select sample type: Metric alert (static threshold)
    • Canal: aluno
    Clique em Test e espere Success. Não feche o painel enquanto o teste roda. Na assinatura de avaliação (Free Trial), o teste falha: o Portal mostra Failed com o erro vazio, e o Activity Log registra Conflict com “Free subscription not supported”. É uma limitação do tipo de assinatura, não do seu Action Group: pule o teste e siga para o 5.2.
CLI 
az monitor action-group create \
  --resource-group {{c.names.rg}} \
  --name {{c.names.ag}} \
  --short-name {{c.names.agShort}} \
  --action email aluno voce@exemplo.com usecommonalertschema

Teste do canal (opcional; falha com Conflict na Free Trial):

az monitor action-group test-notifications create \
  --resource-group {{c.names.rg}} \
  --action-group {{c.names.ag}} \
  --alert-type metricstaticthreshold \
  --add-action email aluno voce@exemplo.com usecommonalertschema

Verifique: chega o e-mail de confirmação de que você foi adicionado ao Action Group (em assinatura paga, chega também o de teste, com “Test” no assunto). Se for o primeiro uso desse endereço no tenant, o Portal mostra Verification email sent: abra o link do e-mail em até 30 minutos, senão o endereço não recebe as notificações do 5.3. Se nada chegar em 5 minutos, olhe o spam; o Ex5 segue mesmo assim, porque o disparo também aparece em Monitor › Alerts.

5.2 · Criar o alerta de Application Deny

O que: crie {{c.names.alertAppDeny}} no firewall {{c.names.fwNs}}, usando a métrica {{c.alerts.appDeny.metric}}.

Por que: este é o alerta didático que deve disparar. Ele soma os hits de Application Rules com {{c.alerts.appDeny.dimension}} = {{c.alerts.appDeny.dimensionValue}}, ou seja, bloqueios explícitos de regra de aplicação, e compara a soma com o limiar.

Com Automatically resolve alerts, o alerta é stateful: dispara uma vez e volta sozinho para Resolved quando a condição deixa de ser verdadeira. Sem essa opção, ele notifica de novo a cada avaliação.

Portal

  1. Comece pelo firewall. Abra Firewalls › {{c.names.fwNs}} › Monitoring › Alerts e clique em + Create › Alert rule. O escopo já vem preenchido com {{c.names.fwNs}}.
    Se você começar por Monitor › Alerts, marque no Scope o firewall, não o resource group nem a assinatura. Com escopo de RG ou assinatura, a lista de sinais mostra só Log search, Resource health e Activity log, sem as métricas do firewall.
  2. Defina a condição. Na aba Condition, clique em See all signals, filtre Signal type = Metrics, selecione Application rules hit count e clique em Apply. Preencha:
    • Threshold: Static
    • Aggregation type: Total
    • Operator: Greater than
    • Threshold value: {{c.alerts.appDeny.threshold}}
    • Split by dimensions: Dimension name {{c.alerts.appDeny.dimension}}, Operator =, Dimension values {{c.alerts.appDeny.dimensionValue}}
    • Check every: 1 minute
    • Lookback period: 5 minutes
    Se {{c.alerts.appDeny.dimensionValue}} não aparecer na lista, use Add custom value.
  3. Ligue o Action Group. Na aba Actions, clique em Select action groups, marque {{c.names.ag}} e clique em Select.
  4. Nomeie a regra. Na aba Details, preencha:
    • Resource group: {{c.names.rg}}
    • Severity: 3 - Informational
    • Alert rule name: {{c.names.alertAppDeny}}
    • Advanced options: Enable upon creation e Automatically resolve alerts marcados
    Clique em Review + create › Create.
CLI 
FW_NS_ID=$(az network firewall show \
  --resource-group {{c.names.rg}} \
  --name {{c.names.fwNs}} \
  --query id -o tsv)

AG_ID=$(az monitor action-group show \
  --resource-group {{c.names.rg}} \
  --name {{c.names.ag}} \
  --query id -o tsv)

az monitor metrics alert create \
  --resource-group {{c.names.rg}} \
  --name {{c.names.alertAppDeny}} \
  --scopes "$FW_NS_ID" \
  --condition "total {{c.alerts.appDeny.metric}} > {{c.alerts.appDeny.threshold}} where {{c.alerts.appDeny.dimension}} includes {{c.alerts.appDeny.dimensionValue}}" \
  --window-size 5m \
  --evaluation-frequency 1m \
  --severity {{c.alerts.appDeny.severity}} \
  --action "$AG_ID" \
  --description "Application rule denies on {{c.names.fwNs}}"

Se o Metrics explorer ainda não listar {{c.alerts.appDeny.dimensionValue}} para a dimensão {{c.alerts.appDeny.dimension}}, crie temporariamente sem o filtro de dimensão:

FW_NS_ID=$(az network firewall show -g {{c.names.rg}} -n {{c.names.fwNs}} --query id -o tsv)
AG_ID=$(az monitor action-group show -g {{c.names.rg}} -n {{c.names.ag}} --query id -o tsv)

az monitor metrics alert create \
  --resource-group {{c.names.rg}} \
  --name {{c.names.alertAppDeny}} \
  --scopes "$FW_NS_ID" \
  --condition "total {{c.alerts.appDeny.metric}} > {{c.alerts.appDeny.threshold}}" \
  --window-size 5m \
  --evaluation-frequency 1m \
  --severity {{c.alerts.appDeny.severity}} \
  --action "$AG_ID" \
  --description "Application rule hits on {{c.names.fwNs}}; sem filtro de Status"

Verifique: o alerta aparece em Monitor › Alerts › Alert rules. Sem a dimensão, qualquer hit de Application Rule entra na soma; isso aumenta ruído e pode disparar com tráfego permitido.

5.3 · Gerar denies a partir da VM-A

O que: execute {{c.targets.denyLoopCount}} requisições para https://{{c.targets.bing}} a partir de {{c.names.vmA}}.

Por que: depois do Ex3, o acesso a {{c.targets.bing}} a partir da VM-A ainda cai na regra {{c.rules.denyBing}}. O Ex3 adicionou um Allow no pai para {{c.targets.baselineFqdn}} e um guardrail de RDP entre spokes; nenhum dos dois permite {{c.targets.bing}}, e a regra temporária de Network Allow do Ex2 já foi removida.

{{c.targets.denyLoopCount}} requisições seguidas passam do limiar de {{c.alerts.appDeny.threshold}} dentro da janela de 5 minutos. Tráfego esparso não dispararia: é para isso que serve o limiar.

Portal

  1. Abra Virtual machines › {{c.names.vmA}} › Connect › Bastion.
  2. Use o usuário {{c.vm.adminUsername}} e a senha criada no Ex0.
  3. Dentro da VM, abra Start › Windows PowerShell e execute o loop abaixo. Ele leva cerca de 2 minutos.
  4. Toda linha deve mostrar DENY/timeout esperado. Se aparecer ALLOW (inesperado), alguma regra de Allow cobre {{c.targets.bing}}: revise os exercícios anteriores antes de seguir.
for ($i = 1; $i -le {{c.targets.denyLoopCount}}; $i++) {
  try {
    Invoke-WebRequest -Uri "https://{{c.targets.bing}}" -UseBasicParsing -TimeoutSec 3 | Out-Null
    Write-Host "$i ALLOW (inesperado)"
  } catch {
    Write-Host "$i DENY/timeout esperado: $($_.Exception.Message)"
  }
  Start-Sleep -Milliseconds 500
}
CLI 
az vm run-command invoke \
  --resource-group {{c.names.rg}} \
  --name {{c.names.vmA}} \
  --command-id RunPowerShellScript \
  --scripts '$ErrorActionPreference = "Continue"
for ($i = 1; $i -le {{c.targets.denyLoopCount}}; $i++) {
  try {
    Invoke-WebRequest -Uri "https://{{c.targets.bing}}" -UseBasicParsing -TimeoutSec 3 | Out-Null
    Write-Host "$i ALLOW (inesperado)"
  } catch {
    Write-Host "$i DENY/timeout esperado: $($_.Exception.Message)"
  }
  Start-Sleep -Milliseconds 500
}' \
  --query "value[0].message" -o tsv

Verifique: aguarde de 5 a 10 minutos para o alerta avaliar a janela de {{c.alerts.appDeny.window}} a cada {{c.alerts.appDeny.frequency}}. Se a regra ou a métrica acabou de ser criada, aguarde até 10–15 minutos. Depois abra Monitor › Alerts, filtre o resource group {{c.names.rg}} e confira {{c.names.alertAppDeny}} com Monitor condition Fired; o e-mail deve chegar pelo Action Group.

Pare o tráfego, espere alguns minutos e clique em Refresh: o Monitor condition volta sozinho para Resolved, porque a regra tem Automatically resolve alerts. Repare que o Alert state continua New: ele é o status de atendimento (New/Acknowledged/Closed) e só muda quando uma pessoa altera. Resolver a condição não fecha o alerta.

5.4 · Configurar o alerta de health

O que: crie {{c.names.alertHealthNs}}, um alerta de prevenção que avisa quando o health do {{c.names.fwNs}} cai abaixo de {{c.alerts.health.threshold}}%.

Por que: o 5.2 avisa sobre um comportamento do tráfego; este avisa sobre a saúde do serviço. {{c.alerts.health.metric}} resume o estado do firewall e cai, por exemplo, quando as portas SNAT de saída se esgotam: acima de {{c.alerts.snat.degradedAbove}}% de {{c.alerts.snat.metric}}, o health fica em 50% com status Degraded e reason SNAT port. Por isso um alerta de health já cobre o caso mais comum de SNAT.

Em produção, crie um alerta de health por firewall (aqui seria também no {{c.names.fwEw}}): o alerta de métrica multirrecurso não cobre Microsoft.Network/azureFirewalls.

Portal

  1. Abra Firewalls › {{c.names.fwNs}} › Monitoring › Alerts › + Create › Alert rule e preencha como no passo 5.2, sem Split by dimensions:
    • Scope: {{c.names.fwNs}}
    • Signal name: Firewall health state
    • Threshold: Static
    • Aggregation type: Average
    • Operator: Less than; Threshold value: {{c.alerts.health.threshold}}
    • Check every: 1 minute; Lookback period: 5 minutes
    • Actions: {{c.names.ag}}
    • Resource group: {{c.names.rg}}
    • Severity: 1 - Error
    • Alert rule name: {{c.names.alertHealthNs}}
    Clique em Review + create › Create.
  2. Abra Monitor › Alerts › Alert rules e confira a regra com Status Enabled.
CLI 
FW_NS_ID=$(az network firewall show -g {{c.names.rg}} -n {{c.names.fwNs}} --query id -o tsv)
AG_ID=$(az monitor action-group show -g {{c.names.rg}} -n {{c.names.ag}} --query id -o tsv)

az monitor metrics alert create \
  -g {{c.names.rg}} \
  -n {{c.names.alertHealthNs}} \
  --scopes "$FW_NS_ID" \
  --condition "avg {{c.alerts.health.metric}} < {{c.alerts.health.threshold}}" \
  --window-size 5m \
  --evaluation-frequency 1m \
  --severity {{c.alerts.health.severity}} \
  --action "$AG_ID" \
  --description "Firewall health on {{c.names.fwNs}}"

Verifique: a regra aparece habilitada em Monitor › Alerts › Alert rules. Ela é de prevenção: não tente derrubar o health do firewall para vê-la disparar.

5.5 · Ler saúde, latência e capacidade do firewall

O que: compare, nos dois firewalls, Firewall health state com as dimensões Status e Reason, Latency Probe e Observed Capacity Units.

Por que: são os primeiros sinais quando alguém diz "a rede está lenta". O Latency Probe estima a latência média do próprio firewall, em milissegundos; ele não mede o caminho fim a fim do usuário até o destino. A dimensão Reason do health diz por que o firewall saiu de 100%, por exemplo SNAT. Observed Capacity Units mostra quanto o serviço escalou.

Portal

  1. Abra Firewalls › {{c.names.fwNs}} › Monitoring › Metrics e ajuste o intervalo para Last 4 hours.
  2. Health. Em Metric, escolha Firewall health state (Avg). Clique em Apply splitting por Status e depois troque para Reason.
  3. Latência e capacidade. Clique em + New chart e escolha Latency Probe (Avg). Faça outro gráfico com Observed Capacity Units.
  4. Repita em Firewalls › {{c.names.fwEw}} › Monitoring › Metrics e compare os dois.
  5. Opcional: rode de novo a consulta do passo 5.4, que também traz essas métricas exportadas para o workspace.
CLI 
FW_NS_ID=$(az network firewall show -g {{c.names.rg}} -n {{c.names.fwNs}} --query id -o tsv)
az monitor metrics list \
  --resource "$FW_NS_ID" \
  --metrics FirewallHealth FirewallLatencyPng ObservedCapacity \
  --interval PT5M \
  --offset 4h \
  -o table
az monitor metrics list \
  --resource "$FW_NS_ID" \
  --metrics FirewallHealth \
  --filter "Status eq '*' and Reason eq '*'" \
  --interval PT5M \
  --offset 4h \
  -o table

Verifique: em condição normal, o health fica em 100% com Status Healthy; a latência e a capacidade ficam estáveis. Anote os valores dos dois firewalls: eles são a sua linha de base para comparar num incidente. Um pico de latência que coincide com reclamação de lentidão é motivo para abrir chamado; latência baixa no firewall com usuário reclamando aponta para outro trecho do caminho.

Checkpoint C5

Execute o checkpoint para confirmar {{c.names.ag}}, os dois alertas e pelo menos um disparo do alerta de deny.

./scripts/checkpoint.sh C5

Critério de avanço: {{c.names.alertAppDeny}} tem histórico de disparo, e o alerta {{c.names.alertHealthNs}} existe e está habilitado.

O que você aprendeu

  • Métrica é o caminho certo quando o sinal já existe, precisa de baixa latência e não exige KQL avançado.
  • Teste do Action Group valida o canal (e não roda em Free Trial); disparo real exige gerar a condição do alerta.
  • Severidade deve refletir impacto operacional: deny didático em severity {{c.alerts.appDeny.severity}} e health em {{c.alerts.health.severity}}.
  • Ruído importa: filtros de dimensão reduzem falsos positivos, mas precisam existir na série temporal.
  • O próximo passo de maturidade é trocar notificação pura por ação automatizada controlada, como webhook, Logic App ou runbook com aprovação e rollback.
