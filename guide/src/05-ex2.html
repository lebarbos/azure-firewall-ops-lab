Ex2 · Precedência das regras

⏱ 50 min · Checkpoint C2

Quando duas regras se contradizem, uma liberando e outra bloqueando, qual o firewall obedece? Neste exercício você prova a resposta com previsão e log. O firewall não lê as regras como uma lista única: ele faz uma passada por tipo, primeiro todas as Network rules e depois todas as Application rules. Dentro de cada passada, conta a prioridade do Rule Collection Group e, dentro do RCG, a da Rule Collection. O primeiro match encerra a avaliação.

Antes de começar

O Ex1 precisa estar concluído: IP Groups criados e {{c.rcg.baselineNs.name}} na policy {{c.names.polNs}}.

Layout que você vai montar

A ideia: os bloqueios ficam no RCG de número melhor ({{c.rcg.wlA.name}}, {{c.rcg.wlA.priority}}) e as liberações no de número pior ({{c.rcg.wlB.name}}, {{c.rcg.wlB.priority}}). Pelo número, os bloqueios deveriam sempre ganhar; os experimentos mostram quando isso não acontece.

2.1 · Criar o RCG {{c.rcg.wlA.name}} (os bloqueios)

O que: crie o RCG {{c.rcg.wlA.name}} com uma collection de Application Deny e duas regras.

Por que: este RCG tem o número melhor do exercício ({{c.rcg.wlA.priority}}). Ele guarda os bloqueios que os experimentos vão tentar contornar: {{c.targets.learn}} só para a VM-A e {{c.targets.bing}} para as duas VMs.

Portal

Uma alteração por vez: espere a anterior terminar

Cada Add atualiza a policy inteira e leva alguns minutos. Enquanto o grupo ou a collection anterior ainda estiver sendo criado, não abra o próximo formulário. Antes de cada + Add, clique em Refresh em Rule collections e confirme, em {{c.names.polNs}} › Overview, que o Provisioning state é Succeeded.

Se aparecer "The firewall policy has been modified since first loading this page. Please refresh to get the latest updates.", o formulário foi aberto antes da alteração anterior terminar. Feche o formulário, espere Succeeded, clique em Refresh e preencha de novo.

  1. Abra Firewall Policies › {{c.names.polNs}} › Rules › Rule collections.
  2. Grupo. Clique em + Add › Rule collection group e preencha:
    • Name: {{c.rcg.wlA.name}}
    • Priority: {{c.rcg.wlA.priority}}
    Clique em Add e espere Succeeded.
  3. Collection. Clique em + Add › Rule collection e preencha o cabeçalho:
    • Name: {{c.rc.appWlA.name}}
    • Rule collection type: Application
    • Priority: {{c.rc.appWlA.priority}}
    • Rule collection action: Deny
    • Rule collection group: {{c.rcg.wlA.name}}
    Na tabela Rules, preencha duas linhas.

    Linha 1 (bloqueia o Learn só para a VM-A):

    • Name: {{c.rules.denyLearn}}
    • Source type: IP Group
    • Source: {{c.names.ipgWlA}}
    • Protocol: Http:80,Https:443
    • Destination Type: FQDN
    • Destination: {{c.targets.learn}}

    Linha 2 (bloqueia o Bing para as duas VMs):

    • Name: {{c.rules.denyBing}}
    • Source type: IP Group
    • Source: {{c.names.ipgSpokes}}
    • Protocol: Http:80,Https:443
    • Destination Type: FQDN
    • Destination: {{c.targets.bing}}
    Deixe TLS inspection desmarcado. Clique em Add e espere Succeeded.

Teste nas duas VMs e anote a diferença

Com o RCG criado, espere a policy voltar a Succeeded e mais 1 a 2 minutos para propagação. Depois:

  1. Conecte na VM-A pelo Bastion, abra o PowerShell e rode o script abaixo.
  2. Conecte na VM-B e rode o mesmo script.
  3. Anote, para cada VM e cada site, se abriu (código 200) ou deu erro. Compare as duas VMs: o que mudou de uma para a outra? No E1 você descobre por quê.
foreach ($site in "https://{{c.targets.learn}}", "https://{{c.targets.bing}}") {
  try { "$site -> " + (Invoke-WebRequest -Uri $site -UseBasicParsing -TimeoutSec 20).StatusCode }
  catch { "$site -> ERRO: " + $_.Exception.Message }
}

Opcional: sem abrir o Bastion, pelo Run command. O tráfego sai da própria VM, então o firewall avalia do mesmo jeito.

  1. Abra Virtual machines › {{c.names.vmA}} › Operations › Run command e escolha RunPowerShellScript.
  2. Cole o mesmo script, clique em Run e espere o resultado em Output.
  3. Repita em {{c.names.vmB}} › Operations › Run command. Pode abrir as duas VMs em abas lado a lado.

Limites do Run command: roda um script por vez em cada VM, leva no mínimo cerca de 20 segundos, não pode ser cancelado e mostra só os últimos 4.096 bytes da saída. Por isso o script imprime só o código ou o erro de cada site. Se o resultado não voltar, use o Bastion. Referência: Run Command no Windows.

Use o mesmo script, pelo Bastion ou pelo Run command, em todos os testes dos experimentos. Antes de cada teste, espere a policy voltar a Succeeded e mais 1 a 2 minutos.

E1 · Leia o resultado: qual regra decidiu e em que ordem

O que: com o resultado do teste que você acabou de fazer nas VMs, descubra qual regra decidiu cada acesso e em que ordem o firewall leu as regras.

Por que: o firewall não lê as regras como uma lista única. Ele dá uma volta por tipo: primeiro todas as Network, depois todas as Application. Dentro de cada volta, segue o número do grupo (RCG) e, dentro do grupo, o da collection. A primeira regra que casa decide. Entender esta ordem no estado atual é a base para prever os próximos experimentos.

E4 · Mesmo tipo, mesmo grupo: o número da collection decide

Duas regras Application no mesmo grupo. Agora o número da collection faz diferença?

Previsão

Em {{c.rcg.wlB.name}} já existe o Allow {{c.rc.appWlBAllow.name}} (collection {{c.rc.appWlBAllow.priority}}) para {{c.targets.learn}}. Você vai criar, no mesmo RCG, o Deny {{c.rc.appWlBDeny.name}} (collection {{c.rc.appWlBDeny.priority}}) para {{c.targets.learn}}, só para a VM-B. A VM-B acessa? E se o Deny mudar para {{c.rc.appWlBDeny.e4Priority}}?

Portal

  1. Crie o Deny. Em Firewall Policies › {{c.names.polNs}} › Rules › Rule collections, clique em + Add › Rule collection e preencha o cabeçalho:
    • Name: {{c.rc.appWlBDeny.name}}
    • Rule collection type: Application
    • Priority: {{c.rc.appWlBDeny.priority}}
    • Rule collection action: Deny
    • Rule collection group: {{c.rcg.wlB.name}}
    Na tabela Rules, preencha uma linha:
    • Name: {{c.rules.denyLearnB}}
    • Source type: IP Group
    • Source: {{c.names.ipgWlB}}
    • Protocol: Http:80,Https:443
    • Destination Type: FQDN
    • Destination: {{c.targets.learn}}
    Clique em Add, espere Succeeded e mais 1 a 2 minutos.
  2. Na VM-B, rode Invoke-WebRequest -Uri https://{{c.targets.learn}} -UseBasicParsing.
  3. Troque o número da collection. Na lista, clique em {{c.rc.appWlBDeny.name}} para editar, mude Priority para {{c.rc.appWlBDeny.e4Priority}}, salve e espere Succeeded. Teste de novo na VM-B.
  4. Obrigatório para o C2: marque {{c.rc.appWlBDeny.name}}, clique em Delete, confirme e espere Succeeded.
CLI 
RG={{c.names.rg}}
POL={{c.names.polNs}}
IPG_WL_B_ID=$(az network ip-group show -g "$RG" -n {{c.names.ipgWlB}} --query id -o tsv)

wait_rcg() {
  local rcg="$1"
  until [ "$(az network firewall policy rule-collection-group show -g "$RG" --policy-name "$POL" -n "$rcg" --query provisioningState -o tsv)" = "Succeeded" ]; do
    sleep 20
  done
  sleep 90
}

test_learn() {
  for VM in "$@"; do
    echo "== $VM =="
    az vm run-command invoke -g "$RG" -n "$VM" --command-id RunPowerShellScript \
      --scripts 'try { Invoke-WebRequest -Uri https://{{c.targets.learn}} -UseBasicParsing -TimeoutSec 20 | Select-Object -ExpandProperty StatusCode } catch { $_.Exception.Message }' \
      --query "value[0].message" -o tsv
  done
}

add_deny() {
  az network firewall policy rule-collection-group collection add-filter-collection \
    -g "$RG" --policy-name "$POL" --rule-collection-group-name {{c.rcg.wlB.name}} \
    -n {{c.rc.appWlBDeny.name}} --collection-priority "$1" --action Deny \
    --rule-name {{c.rules.denyLearnB}} --rule-type ApplicationRule \
    --source-ip-groups "$IPG_WL_B_ID" --protocols Http=80 Https=443 \
    --target-fqdns {{c.targets.learn}} \
    -o none
  wait_rcg {{c.rcg.wlB.name}}
}

remove_deny() {
  az network firewall policy rule-collection-group collection remove \
    -g "$RG" --policy-name "$POL" --rule-collection-group-name {{c.rcg.wlB.name}} \
    -n {{c.rc.appWlBDeny.name}} \
    -o none
  wait_rcg {{c.rcg.wlB.name}}
}

echo "Deny em {{c.rc.appWlBDeny.priority}}"
add_deny {{c.rc.appWlBDeny.priority}}
test_learn {{c.names.vmB}}

echo "Deny em {{c.rc.appWlBDeny.e4Priority}}"
remove_deny
add_deny {{c.rc.appWlBDeny.e4Priority}}
test_learn {{c.names.vmB}}

2.3 · Bônus: ver o handshake TCP com Flow trace

O que: habilite o Flow trace no {{c.names.fwEw}}, repita o teste RDP da VM-A para a VM-B e leia o handshake TCP completo em {{c.diagnostics.flowTrace.category}}. No fim, desligue tudo.

Por que: as tabelas de regra registram a decisão no primeiro pacote (SYN). Quando a conexão "não fecha", você precisa ver o resto do handshake: SYN-ACK, FIN/FIN-ACK, RST ou INVALID, que aparece, por exemplo, em roteamento assimétrico. O Flow trace mostra isso, mas só para regras de rede e de NAT (L3/L4), não para application rules. Gera muito log com conexões curtas: ligue só para investigar.

Opcional e com efeito na assinatura

O registro do recurso {{c.diagnostics.flowTrace.feature}} se aplica à assinatura inteira, não só ao lab, e pode levar vários minutos. Faça este bônus só se houver tempo e desfaça no último passo. Na sua assinatura de trial, isso não afeta outros ambientes.

Portal

  1. Abra Subscriptions › (sua assinatura) › Settings › Preview features, procure Enable TCP Connection Logging, selecione e clique em Register. Aguarde o estado Registered.
  2. Abra Firewalls › {{c.names.fwEw}} › Monitoring › Diagnostic settings, edite {{c.names.diag}}, marque também a categoria de flow trace ({{c.diagnostics.flowTrace.category}}) e salve.
  3. Conecte na VM-A pelo Bastion e rode Test-NetConnection {{c.network.vmBIp}} -Port {{c.targets.rdpPort}} duas ou três vezes.
  4. Abra {{c.names.law}} › Logs e rode a consulta abaixo. Se continuar vazia depois de 15 minutos, consulte Logs não aparecem: o recurso pode precisar de uma atualização do firewall para valer.
  5. Para desligar: desmarque a categoria no diagnostic setting e, em Preview features, clique em Unregister no mesmo recurso.

O C2 exige {{c.rcg.wlB.name}} de volta em prioridade {{c.rcg.wlB.priority}} e as collections temporárias {{c.rc.netWlBTemp.name}} e {{c.rc.appWlBDeny.name}} removidas. Ele confere só o estado final da policy, para que o Ex3 comece limpo.

O que você aprendeu

  • O Azure Firewall Policy faz uma passada por tipo: todas as Network rules antes de todas as Application rules (e o DNAT antes das duas).
  • Dentro de cada tipo, o RCG manda; a prioridade da RC só desempata dentro do RCG avaliado.
  • O primeiro match vence e encerra a avaliação.
  • Network rules amplas podem mascarar application rules; valide por KQL, não só por sintoma.
  • Timeout ou "não abriu" é sintoma; quem decidiu de fato está no log, com Policy, RCG, RC e Rule.
