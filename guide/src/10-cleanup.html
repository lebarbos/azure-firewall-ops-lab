Obrigatório antes de encerrar

O ambiente esquecido ligado custa cerca de US$ {{c.cost.forgottenUsdPerDay}} por dia. Pedir a exclusão não prova que o cleanup terminou: a exclusão do resource group é assíncrona e alguns objetos, como Key Vault em soft-delete, podem continuar ocupando o nome até o purge.

1 · Execute o cleanup automatizado

O que: rode o script que exclui o resource group, espera a exclusão terminar, faz purge dos Key Vaults do Ex6 e procura recursos remanescentes pela tag do lab.

Por que: o lab combina recursos caros no resource group {{c.names.rg}} com objetos globais de Key Vault criados no Ex6. Um delete solicitado e ainda em progresso continua sendo risco de custo ou de bloqueio de nome.

Portal

  1. Use o Cloud Shell em Bash, no clone do lab: ~/{{c.repo.cloneDir}}.
  2. Execute o script abaixo. Ele confirma a exclusão, dispara o delete do RG com operação assíncrona, faz polling até o RG desaparecer, procura Key Vaults apagados com prefixo {{c.names.kvPrefix}} e faz purge quando permitido, depois lista qualquer recurso ainda marcado com workshop={{c.tags.workshop}}.
./scripts/cleanup.sh

Se o Cloud Shell desconectar durante a espera

A exclusão do hub e dos firewalls pode passar de 20 minutos, e o Cloud Shell encerra sessões sem interação após 20 minutos. A exclusão continua no Azure. Reabra o Cloud Shell, volte ao clone (ou clone de novo, veja Cloud Shell caiu) e rode ./scripts/cleanup.sh outra vez: o script detecta a exclusão em andamento e retoma a espera.

CLI 
# Modo não interativo, útil quando o instrutor já confirmou verbalmente.
./scripts/cleanup.sh --yes

Verifique: o script só deve encerrar com sucesso depois de confirmar que {{c.names.rg}} não existe, que não há Key Vault apagado com prefixo {{c.names.kvPrefix}} que possa ser purgado por você e que a varredura por tag não encontrou recursos do lab.

2 · Alternativa pelo Portal

O que: se o script não estiver disponível, remova o resource group e purgue manualmente os Key Vaults apagados do Ex6.

Por que: o Portal ajuda a visualizar o estado, mas ele também inicia operações assíncronas. Você precisa confirmar o estado final, não apenas clicar em Delete.

Portal

  1. Abra Resource groups › {{c.names.rg}} › Overview.
  2. Clique em Delete resource group, digite {{c.names.rg}} e confirme. Aguarde até o RG não aparecer mais na lista.
  3. Abra Key vaults, sem entrar em um vault específico, e selecione Manage deleted vaults.
  4. Filtre pela assinatura e procure nomes que comecem com {{c.names.kvPrefix}} e que vieram do resource group {{c.names.rg}}. O prefixo é o padrão do Portal, então pode haver vaults de outros projetos com o mesmo início: não purgue esses. Se aparecerem e você tiver permissão, selecione e clique em Purge.
  5. Em All resources, filtre por tag workshop igual a {{c.tags.workshop}}. A lista deve ficar vazia para os recursos do lab.
CLI

Esta é a alternativa pelo Portal. Use o próximo passo para o equivalente por CLI.

Verifique: o RG ausente depois do cleanup é status correto. Não é motivo para novo deploy. Se você precisar retomar o lab depois de limpar, comece novamente pelo Ex0 em uma nova sessão.

3 · Alternativa por CLI

O que: use comandos equivalentes ao script quando precisar diagnosticar uma falha ou repetir uma etapa específica.

Por que: estes comandos deixam claro o contrato do cleanup: excluir o RG, esperar até az group exists retornar false, purgar Key Vaults soft-deleted e varrer recursos por tag.

Portal

Se estiver usando apenas Portal, siga o passo anterior. Antes de colar comandos, confirme a sintaxe atual com --help, especialmente em ambientes com versões diferentes do Azure CLI.

CLI 
# 1) Excluir o resource group de forma assíncrona.
az group delete --name {{c.names.rg}} --yes --no-wait

# 2) Esperar até o Azure informar que o RG não existe mais.
while [ "$(az group exists --name {{c.names.rg}} -o tsv)" = "true" ]; do
  echo "Aguardando exclusão de {{c.names.rg}}..."
  sleep 30
done

# 3) Listar Key Vaults soft-deleted criados pelo Ex6.
az keyvault list-deleted --resource-type vault \
  --query "[?starts_with(name, '{{c.names.kvPrefix}}') && contains(properties.vaultId, '/resourceGroups/{{c.names.rg}}/')].{name:name,location:properties.location}" \
  -o table

# 4) Purgar cada vault listado, se purge protection não bloquear e se você tiver permissão.
az keyvault list-deleted --resource-type vault \
  --query "[?starts_with(name, '{{c.names.kvPrefix}}') && contains(properties.vaultId, '/resourceGroups/{{c.names.rg}}/')].[name,properties.location]" -o tsv |
while read -r KV_NAME KV_LOCATION; do
  az keyvault purge --name "$KV_NAME" --location "$KV_LOCATION"
done

# 5) Varredura final por tag do workshop.
az resource list --tag workshop={{c.tags.workshop}} \
  --query "[].{name:name,type:type,resourceGroup:resourceGroup,location:location}" \
  -o table

Verifique: az group exists --name {{c.names.rg}} retorna false e az resource list --tag workshop={{c.tags.workshop}} não mostra recursos do lab.

4 · Entenda o que pode sobrar fora do RG

O que: diferencie sobra cobrável do lab, estado soft-deleted e artefatos gratuitos/externos ao lab.

Por que: nem todo item que você vê no Portal foi criado pelo lab ou gera custo relevante. O checkpoint CX foca o contrato do lab: RG inexistente, Key Vault purgado quando aplicável e zero recursos com a tag workshop={{c.tags.workshop}}.

Portal

  • NetworkWatcherRG: pode existir porque o Azure cria Network Watcher por região. Ele fica fora do RG do lab e, sozinho, não representa o ambiente do workshop. Se quiser remover, abra Resource groups › NetworkWatcherRG e exclua apenas se souber que não há outros usos na assinatura.
  • Storage do Cloud Shell: se você escolheu montar storage, ele persiste fora do lab para guardar o clouddrive. Não é excluído pelo cleanup do workshop. Para remover, use Cloud Shell › Settings › Reset user settings e depois exclua manualmente a storage account/fileshare correspondente, se não precisar mais dela.
  • Key Vault com purge protection: se purge protection estiver habilitado, o purge não pode ser forçado antes do fim da retenção. Registre o nome e purgue depois do fim da retenção.
CLI 
# Conferir se há recursos marcados como parte do workshop.
az resource list --tag workshop={{c.tags.workshop}} -o table

# Conferir Key Vaults apagados que ainda ocupam nome.
az keyvault list-deleted --resource-type vault -o table

Verifique: se sobrar algo fora de {{c.names.rg}}, ele deve ter explicação clara: não é do lab, é gratuito/externo, ou é uma exceção de Key Vault aguardando retenção.

Checkpoint CX

Rode o checkpoint final. Ele confirma o estado, não dispara novo deploy.

./scripts/checkpoint.sh CX

Resultado esperado: {{c.names.rg}} inexistente, zero recursos com workshop={{c.tags.workshop}} e nenhum Key Vault {{c.names.kvPrefix}}* purgável pendente. Se o RG já estava ausente, isso é sucesso de cleanup, não erro.
