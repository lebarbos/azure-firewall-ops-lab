Ex1 · Observabilidade e primeiras regras

75 min · Checkpoint C1

Objetivo: habilitar logs estruturados nos dois firewalls, observar o default deny, criar os objetos base e permitir apenas os fluxos necessários para o restante do lab.

Fontes usadas neste exercício

Os passos de logs estruturados e workbook seguem Monitor Azure Firewall, Azure Firewall monitoring data reference e Use Azure Firewall workbooks. O comportamento de default deny e a ordem DNAT → Network → Application vêm de Configure Azure Firewall rules.

1.1 · Configurar diagnostic settings e Policy Analytics

O que: envie logs estruturados e métricas de {{c.names.fwEw}} e {{c.names.fwNs}} para {{c.names.law}} e habilite o Policy Analytics em {{c.names.polNs}}.

Por que: o lab depende das tabelas resource-specific AZFW*. Elas preservam colunas como action, rule collection group, collection e rule, que tornam a investigação muito mais direta que o formato legado em AzureDiagnostics.

O Policy Analytics é habilitado agora, mas só será lido no Ex4: ele só analisa o tráfego que passa depois de habilitado e agrega os dados de hora em hora. Ele depende das categorias de agregação (AZFW*Aggregation) deste mesmo diagnostic setting. Custa cerca de US$ {{c.cost.items.5.usdPerHour}}/h por policy, por isso o lab habilita só na policy N-S, onde ficam o Ex2 e o Ex3.

Portal

  1. Abra Firewalls › {{c.names.fwEw}} › Monitoring › Diagnostic settings.
  2. Clique em + Add diagnostic setting e use o nome {{c.names.diag}}.
  3. Marque as categorias estruturadas mínimas: {{c.diagnostics.requiredCategories}}.
  4. Se aparecerem outras categorias AZFW*, como DNS, você pode marcá-las para investigação extra. Não marque agora a categoria de flow trace ({{c.diagnostics.flowTrace.category}}): ela fica vazia até registrar um recurso na assinatura, o que é feito no bônus 2.3. Não marque as categorias legadas que gravam em AzureDiagnostics neste lab; misturar formatos exige settings separados e confunde as consultas.
  5. Marque AllMetrics.
  6. Em destino, marque Send to Log Analytics workspace, selecione {{c.names.law}} e escolha Resource specific em Destination table.
  7. Clique em Save.
  8. Repita os passos 1 a 7 em Firewalls › {{c.names.fwNs}} › Monitoring › Diagnostic settings, com o mesmo nome {{c.names.diag}}, as mesmas categorias e o mesmo workspace.
  9. Habilite o Policy Analytics. Abra Firewall Policies › {{c.names.polNs}} › Monitoring › Policy Analytics e clique em Configure Workspaces:
    • Enable Policy Analytics: marcado
    • Workspace: {{c.names.law}}, o mesmo dos diagnostic settings
    Clique em Save. A tela continua vazia até a primeira agregação, cerca de 60 min depois; os dados são lidos no Ex4.

Não esqueça o firewall N-S

O diagnostic setting é configurado por firewall. Ao terminar o {{c.names.fwEw}}, faça o mesmo no {{c.names.fwNs}}. Sem isso, as consultas de saída para a Internet e de application rules voltam vazias nos próximos exercícios.

1.2 · Testar antes das regras e comparar rotas efetivas

O que: acesse a VM-A via Bastion, gere tráfego que deve ser negado e confira as rotas efetivas da NIC A.

Por que: Bastion funciona sem regra de Azure Firewall porque o caminho administrativo usa peering entre a VNet N-S e o spoke. Já o tráfego A↔B e Internet cruza os firewalls e, sem regras, cai no default deny.

Portal

  1. Abra Virtual machines › {{c.names.vmA}} › Connect › Bastion.
  2. Use o usuário {{c.vm.adminUsername}} e a senha criada no Ex0.
  3. Dentro da VM, abra Start › Windows PowerShell e execute os comandos abaixo.
  4. Depois, compare as rotas em Virtual machines › {{c.names.vmA}} › Networking › Network interface › Effective routes com a tabela da seção Arquitetura.
ping {{c.network.vmBIp}}
Test-NetConnection {{c.network.vmBIp}} -Port {{c.targets.rdpPort}}
Invoke-WebRequest https://{{c.targets.learn}} -UseBasicParsing
curl.exe --connect-timeout 10 --max-time 20 http://{{c.network.vmBIp}}/
CLI 
az vm run-command invoke \
  -g {{c.names.rg}} \
  -n {{c.names.vmA}} \
  --command-id RunPowerShellScript \
  --scripts 'ping {{c.network.vmBIp}}; Test-NetConnection {{c.network.vmBIp}} -Port {{c.targets.rdpPort}}; try { Invoke-WebRequest https://{{c.targets.learn}} -UseBasicParsing -TimeoutSec 20 } catch { $_.Exception.Message }; curl.exe --connect-timeout 10 --max-time 20 http://{{c.network.vmBIp}}/' \
  --query "value[0].message" \
  -o tsv
az network nic show-effective-route-table \
  -g {{c.names.rg}} \
  -n {{c.names.nicA}} \
  -o table

Verifique: Bastion conecta, mas ping, Test-NetConnection, Invoke-WebRequest e o curl.exe HTTP ainda falham ou retornam negação. Nas rotas, você deve reconhecer o prefixo local {{c.network.vnetA}}, o peering para {{c.network.vnetNs}}, os ranges privados aprendidos pelo hub e 0.0.0.0/0 apontando para o firewall N-S.

Previsão

Por que o RDP via Bastion funciona sem nenhuma regra de Azure Firewall?

Ver resposta

Porque a administração entra pelo Bastion em {{c.names.vnetNs}} e chega à VM-A pelo peering com {{c.names.vnetA}}. Esse caminho não passa pelo firewall do hub nem pelo firewall N-S. O objetivo é separar acesso administrativo do fluxo que será inspecionado no exercício.

Referência: VNet peering and Azure Bastion architecture.

1.3 · Criar os IP Groups do baseline

O que: crie três IP Groups para representar Workload A, Workload B e spokes.

Por que: IP Groups simplificam regras de Azure Firewall: podem ser origem em regras de aplicação, origem/destino em regras de rede e origem em DNAT. Se um grupo em uso ficar vazio, a regra é ignorada; por isso o checkpoint também verifica membros.

Portal

  1. Abra IP Groups › + Create.
  2. Crie {{c.names.ipgWlA}} no Resource Group {{c.names.rg}}, na mesma região do RG, com {{c.ipGroupCidrs.ipgWlA}}.
  3. Crie {{c.names.ipgWlB}} com {{c.ipGroupCidrs.ipgWlB}}.
  4. Crie {{c.names.ipgSpokes}} com {{c.ipGroupCidrs.ipgSpokes}}.
CLI 
REGION=$(az group show -n {{c.names.rg}} --query location -o tsv)
az network ip-group create \
  -g {{c.names.rg}} \
  -n {{c.names.ipgWlA}} \
  -l "$REGION" \
  --ip-addresses {{c.network.snetA}}
REGION=$(az group show -n {{c.names.rg}} --query location -o tsv)
az network ip-group create \
  -g {{c.names.rg}} \
  -n {{c.names.ipgWlB}} \
  -l "$REGION" \
  --ip-addresses {{c.network.snetB}}
REGION=$(az group show -n {{c.names.rg}} --query location -o tsv)
az network ip-group create \
  -g {{c.names.rg}} \
  -n {{c.names.ipgSpokes}} \
  -l "$REGION" \
  --ip-addresses {{c.network.snetA}} {{c.network.snetB}}

Verifique: os três IP Groups existem, estão no mesmo Resource Group do lab e têm exatamente os CIDRs do contrato.

1.4 · Criar as primeiras regras

O que: crie um baseline E-W para ICMP/RDP e um baseline N-S para FQDNs Microsoft.

Por que: Azure Firewall processa DNAT, depois Network e depois Application. Neste exercício, o E-W usa regra Network para tráfego entre spokes, e a saída N-S usa regra Application por FQDN. As prioridades do contrato deixam espaço para os experimentos posteriores.

Portal

  1. Abra Firewall Policies › {{c.names.polEw}} › Rules › Rule collections.
  2. Clique em + Add › Rule collection group, use o nome {{c.rcg.baselineEw.name}} e a prioridade {{c.rcg.baselineEw.priority}} e clique em Add.
  3. Clique em + Add › Rule collection: nome {{c.rc.netBaselineEw.name}}, tipo Network, prioridade {{c.rc.netBaselineEw.priority}}, ação Allow e, em Rule collection group, {{c.rcg.baselineEw.name}}.
  4. No mesmo formulário, crie a regra {{c.rules.allowIcmp}}: protocolo ICMP, origem {{c.names.ipgSpokes}}, destino {{c.names.ipgSpokes}}, portas *.
  5. Crie também a regra {{c.rules.allowRdp}}: protocolo TCP, porta {{c.targets.rdpPort}}, origem {{c.names.ipgSpokes}}, destino {{c.names.ipgSpokes}}. Clique em Add.
  6. Abra Firewall Policies › {{c.names.polNs}} › Rules › Rule collections.
  7. Clique em + Add › Rule collection group, use o nome {{c.rcg.baselineNs.name}} e a prioridade {{c.rcg.baselineNs.priority}} e clique em Add.
  8. Clique em + Add › Rule collection: nome {{c.rc.appBaseline.name}}, tipo Application, prioridade {{c.rc.appBaseline.priority}}, ação Allow e, em Rule collection group, {{c.rcg.baselineNs.name}}.
  9. No mesmo formulário, crie a regra {{c.rules.allowMicrosoft}}: origem {{c.names.ipgSpokes}}, protocolos HTTP:80 e HTTPS:443, destino FQDN {{c.targets.baselineFqdn}}. Clique em Add.
  10. Aguarde o provisioning da policy voltar para Succeeded e mais 1–2 minutos para propagação.
CLI 
IPG_SPOKES_ID=$(az network ip-group show -g {{c.names.rg}} -n {{c.names.ipgSpokes}} --query id -o tsv)
az network firewall policy rule-collection-group create \
  -g {{c.names.rg}} \
  --policy-name {{c.names.polEw}} \
  --name {{c.rcg.baselineEw.name}} \
  --priority {{c.rcg.baselineEw.priority}}
az network firewall policy rule-collection-group collection add-filter-collection \
  -g {{c.names.rg}} \
  --policy-name {{c.names.polEw}} \
  --rule-collection-group-name {{c.rcg.baselineEw.name}} \
  --name {{c.rc.netBaselineEw.name}} \
  --action Allow \
  --collection-priority {{c.rc.netBaselineEw.priority}} \
  --rule-name {{c.rules.allowIcmp}} \
  --rule-type NetworkRule \
  --source-ip-groups "$IPG_SPOKES_ID" \
  --destination-ip-groups "$IPG_SPOKES_ID" \
  --ip-protocols ICMP \
  --destination-ports "*"
az network firewall policy rule-collection-group collection rule add \
  -g {{c.names.rg}} \
  --policy-name {{c.names.polEw}} \
  --rule-collection-group-name {{c.rcg.baselineEw.name}} \
  --name {{c.rc.netBaselineEw.name}} \
  --rule-name {{c.rules.allowRdp}} \
  --rule-type NetworkRule \
  --source-ip-groups "$IPG_SPOKES_ID" \
  --destination-ip-groups "$IPG_SPOKES_ID" \
  --ip-protocols TCP \
  --destination-ports {{c.targets.rdpPort}}
IPG_SPOKES_ID=$(az network ip-group show -g {{c.names.rg}} -n {{c.names.ipgSpokes}} --query id -o tsv)
az network firewall policy rule-collection-group create \
  -g {{c.names.rg}} \
  --policy-name {{c.names.polNs}} \
  --name {{c.rcg.baselineNs.name}} \
  --priority {{c.rcg.baselineNs.priority}}
az network firewall policy rule-collection-group collection add-filter-collection \
  -g {{c.names.rg}} \
  --policy-name {{c.names.polNs}} \
  --rule-collection-group-name {{c.rcg.baselineNs.name}} \
  --name {{c.rc.appBaseline.name}} \
  --action Allow \
  --collection-priority {{c.rc.appBaseline.priority}} \
  --rule-name {{c.rules.allowMicrosoft}} \
  --rule-type ApplicationRule \
  --source-ip-groups "$IPG_SPOKES_ID" \
  --protocols Http=80 Https=443 \
  --target-fqdns '{{c.targets.baselineFqdn}}'
az network firewall policy wait -g {{c.names.rg}} -n {{c.names.polEw}} --updated --interval 30 --timeout 1800
az network firewall policy wait -g {{c.names.rg}} -n {{c.names.polNs}} --updated --interval 30 --timeout 1800
sleep 120

Verifique: os dois RCGs existem com prioridade {{c.rcg.baselineEw.priority}}/{{c.rcg.baselineNs.priority}}, as collections têm prioridade {{c.rc.netBaselineEw.priority}}/{{c.rc.appBaseline.priority}} e as regras usam os IP Groups, não CIDRs digitados manualmente. Espere o firewall/policy voltar a Succeeded e mais 1 a 2 minutos antes de testar.

O que: confirme que os fluxos permitidos passaram e que o restante continua negado.

Por que: o objetivo não é abrir Internet genericamente. O baseline permite ICMP/RDP entre spokes e FQDNs Microsoft pela regra de aplicação; {{c.targets.bing}} continua fora do escopo.

1.6 · Ler as decisões com KQL e workbook

O que: use três consultas KQL e o workbook embutido para explicar qual firewall decidiu cada fluxo.

Por que: o workbook é ótimo para exploração visual, mas a prova do exercício é a combinação de timestamp, firewall, origem, destino/FQDN, ação, policy, RCG, collection e regra.

Portal

  1. Abra Log Analytics workspaces › {{c.names.law}} › Logs.
  2. Cole cada consulta abaixo e ajuste apenas a janela de tempo, se necessário.
  3. Depois abra Firewalls › {{c.names.fwNs}} › Monitoring › Workbooks e escolha o workbook do Azure Firewall na galeria.
  4. No workbook, selecione o workspace {{c.names.law}} e os firewalls {{c.names.fwNs}} e {{c.names.fwEw}}.
CLI

O caminho principal é Portal porque o objetivo é ensinar leitura de logs e workbook. Se o instrutor quiser automatizar a consulta, use az monitor log-analytics query depois de confirmar a extensão e o workspace no seu ambiente.

Verifique: em ex1-allow-deny, compare Allow × Deny por _ResourceId para separar E-W de N-S. Em ex1-default-deny, procure negações sem regra casada para identificar default deny. Em ex1-timeline, leia a sequência recente e responda: qual firewall decidiu, por qual policy/RCG/collection/rule e por quê.

O C1 verifica: diagnostic setting nos dois firewalls em modo Resource specific para {{c.names.law}}, Policy Analytics habilitado em {{c.names.polNs}} com o workspace do lab, três IP Groups criados, {{c.rcg.baselineEw.name}} nas duas policies e KQL com pelo menos um Allow e um Deny nos últimos 30 minutos.

O que você aprendeu

  • Bastion via peering é caminho administrativo e não prova regra de firewall.
  • Sem regra, Azure Firewall nega por padrão; o log estruturado mostra o motivo.
  • IP Groups reduzem repetição e viram objetos reutilizáveis nas regras.
  • Network rules e Application rules têm papéis diferentes; abrir FQDN não é o mesmo que liberar 443 para qualquer destino.
  • Workbook mostra tendências; KQL mostra a decisão exata que sustenta o troubleshooting.
