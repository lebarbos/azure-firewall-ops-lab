Ex0 · Preparação e deploy

20 min · Checkpoint C0 · a teoria acontece enquanto o deploy roda

Objetivo: preparar o Cloud Shell, validar região/SKU, disparar o deployment da base e acompanhar a criação sem deixar segredo em arquivo, argumento ou histórico.

Atenção ao Cloud Shell

Use Bash. Uma sessão efêmera serve para este lab, mas o Cloud Shell encerra após 20 minutos sem atividade interativa e o diretório $HOME pode ser perdido quando a sessão termina. Se cair, reabra o Cloud Shell, clone o repositório de novo e rode os scripts novamente: eles leem o estado do Azure quando o Resource Group já existe.

Referência: Azure Cloud Shell FAQ.

0.1 · Abrir o Cloud Shell em Bash

O que: abra uma sessão do Azure Cloud Shell usando Bash.

Por que: todos os scripts foram escritos para Bash no Cloud Shell. Eles não dependem de estado permanente local e podem ser reexecutados se a sessão expirar.

Portal

  1. Abra o Azure portal › Cloud Shell.
  2. Escolha Bash. Se aparecer a escolha de storage, a opção efêmera é suficiente para o lab; o importante é saber que o clone pode sumir ao encerrar a sessão.
  3. Confirme visualmente a assinatura ativa antes de executar qualquer script.
CLI

Sem equivalente direto no CLI: este passo abre a interface interativa do Cloud Shell no Portal.

Verifique: o prompt mostra uma sessão Bash pronta para comandos. Se você fechar ou ficar ocioso por muito tempo, reabra, clone novamente e continue pelo script adequado.

0.2 · Instalar o Bicep e as extensões do Azure CLI

O que: instale o Bicep CLI e as extensões usadas pelo lab, um comando por vez.

Por que: o guia evita instalação automática escondida. Se o preflight encontrar uma extensão ausente, você sabe exatamente qual comando repetir. A base do lab é um arquivo Bicep: sem o Bicep CLI, o preflight para com Bicep CLI not found.

Portal

  1. No Cloud Shell em Bash, cole um bloco por vez.
  2. Se o comando avisar que a extensão já existe, o parâmetro --upgrade mantém a versão atualizada.
  3. Se o Cloud Shell for recriado (sessão efêmera ou timeout), repita este passo antes do preflight.
CLI 
az bicep install
az bicep version
az extension add --name azure-firewall --upgrade
az extension add --name virtual-wan --upgrade
az extension add --name bastion --upgrade
az extension add --name log-analytics --upgrade

Verifique: az bicep version mostra a versão instalada e nenhum comando termina com erro. A lista de extensões vem de {{c.cliExtensions}}.

0.3 · Clonar o repositório do lab

O que: baixe o pacote do lab no diretório padrão do Cloud Shell.

Por que: os scripts assumem que você executa os comandos a partir da raiz do repositório, onde ficam lab.contract.json, infra/ e scripts/.

Portal

  1. No Cloud Shell, use Manage files › Upload apenas se o GitHub estiver indisponível para você.
  2. Se usar ZIP, envie o arquivo, extraia-o e entre na pasta extraída antes de continuar.
CLI 
cd ~
rm -rf {{c.repo.cloneDir}}
git clone {{c.repo.url}} {{c.repo.cloneDir}}
cd {{c.repo.cloneDir}}
# Alternativa se você subiu o ZIP pelo botão de upload do Cloud Shell:
cd ~
ZIP="$(ls -t ~/{{c.repo.cloneDir}}*.zip | head -n 1)"
echo "Usando $ZIP"
rm -rf {{c.repo.cloneDir}}
unzip -q -o "$ZIP" -d {{c.repo.cloneDir}}
cd {{c.repo.cloneDir}}

Verifique: pwd termina em {{c.repo.cloneDir}} e ls scripts infra lab.contract.json lista os arquivos esperados.

0.4 · Rodar o preflight

O que: valide região, SKU, providers e permissões antes de criar recursos.

Por que: o deploy usa dois Azure Firewalls Premium, vWAN, Bastion e duas VMs. O preflight tenta escolher a primeira combinação viável de região e SKU, grava .lab/env sem segredo e mostra uma tabela de decisão.

Portal

  1. Use o Portal apenas para conferir a assinatura: Subscriptions › Overview.
  2. Se nenhuma região passar, confira quota em Subscriptions › Usage + quotas e chame o instrutor antes de mudar a arquitetura.
CLI 
cd ~/{{c.repo.cloneDir}}
./scripts/preflight.sh
# Se o instrutor orientar uma região específica, force a validação assim:
cd ~/{{c.repo.cloneDir}}
LAB_REGION={{c.regions.0}} ./scripts/preflight.sh

Verifique: leia a tabela linha a linha. ✅ significa que aquela combinação passou nas checagens do script; ❌ vem com o motivo a corrigir ou escalar. Se nenhuma região servir, não aumente a VM nem troque endereçamento por conta própria: peça ao instrutor uma assinatura/região alternativa ou ajuste autorizado em lab.contract.json.

Ao final, o arquivo .lab/env deve conter LAB_REGION, LAB_VM_SIZE e LAB_TRUSTED_LAUNCH, sem senha.

0.5 · Disparar o deploy da base

O que: execute o script que pede a senha e envia o deployment de assinatura.

Por que: a senha do usuário {{c.vm.adminUsername}} é lida duas vezes sem eco, validada localmente e exportada apenas para o processo do az. O template lê a senha por variável de ambiente; ela não aparece na linha de comando, em arquivo de parâmetro ou em output. O --no-wait libera o Cloud Shell enquanto o Azure continua criando os recursos.

Portal

  1. Antes de executar, deixe aberto Subscriptions › Deployments.
  2. Depois do comando, acompanhe também Resource groups › {{c.names.rg}} › Deployments e Resource groups › {{c.names.rg}} › Resources.
CLI 
cd ~/{{c.repo.cloneDir}}
./scripts/deploy.sh

Regras da senha: 12 a 123 caracteres, pelo menos 3 de 4 classes de caracteres, sem o nome do usuário {{c.vm.adminUsername}} e sem começar com @.

CLI equivalente ao trecho crítico do deploy.sh 
cd ~/{{c.repo.cloneDir}}
source .lab/env
read -rsp "Senha de {{c.vm.adminUsername}}: " LAB_ADMIN_PASSWORD; echo
export LAB_REGION LAB_VM_SIZE LAB_TRUSTED_LAUNCH LAB_ADMIN_PASSWORD
export LAB_EXPIRES_ON="$(date -u -d '+1 day' +%F)"
az deployment sub create \
  --location "$LAB_REGION" \
  --name "{{c.names.deploymentPrefix}}-$(date -u +%Y%m%d%H%M%S)" \
  --parameters infra/main.bicepparam \
  --no-wait
unset LAB_ADMIN_PASSWORD

O script real também pede confirmação da senha, aplica a validação local e recusa sobrescrever um {{c.names.rg}} existente sem --force.

Verifique: o comando retorna sem expor a senha e informa o nome do deployment. O tempo estimado da base é 45 a 75 minutos.

0.6 · Acompanhar o deploy sem reiniciar a base

O que: acompanhe o deployment pelo Portal ou por consultas somente leitura.

Por que: o Cloud Shell pode cair, mas o deployment continua no Azure. A retomada correta é consultar o estado ou reabrir a pasta e rodar os scripts reexecutáveis, não apagar o ambiente nem disparar outro lab paralelo.

Portal

  1. Abra Subscriptions › Deployments e filtre por {{c.names.deploymentPrefix}}.
  2. Abra o deployment mais recente e acompanhe Deployment details.
  3. Abra Resource groups › {{c.names.rg}} › Resources para ver os recursos surgirem.
CLI 
az deployment sub list \
  --query "[?starts_with(name, '{{c.names.deploymentPrefix}}-')].[name,properties.provisioningState,properties.timestamp]" \
  -o table
DEPLOYMENT_NAME=$(az deployment sub list \
  --query "reverse(sort_by([?starts_with(name, '{{c.names.deploymentPrefix}}-')], &properties.timestamp))[0].name" \
  -o tsv)
az deployment sub show \
  --name "$DEPLOYMENT_NAME" \
  --query "{name:name,state:properties.provisioningState,outputs:properties.outputs}" \
  -o jsonc

Verifique: o deployment chega a Succeeded. Se aparecer Failed, abra a operação com erro e preserve a mensagem completa para o instrutor.

Checkpoint C0 · Base pronta

cd ~/{{c.repo.cloneDir}}
./scripts/checkpoint.sh C0

O C0 verifica: deployment Succeeded, os dois firewalls em Succeeded, routing intent {{c.names.routingIntent}} apontando PrivateTraffic para o firewall E-W, conexões do hub, rotas efetivas da NIC A, extensão {{c.names.cse}} com marcador {{c.vm.bootstrapMarker}} e IIS respondendo em localhost via Run Command.

Só avance para o Ex1 quando o checkpoint estiver verde ou quando o instrutor declarar a contingência.
