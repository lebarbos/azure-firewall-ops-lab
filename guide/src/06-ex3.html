Ex3 · Policy pai e filhas

⏱ 45 min · Checkpoint C3

Neste exercício, você vai centralizar a governança com Firewall Manager: a policy pai impõe os guardrails corporativos, e as policies filhas mantêm as regras específicas de cada workload.

Você começa com o estado deixado pelo Ex1 e Ex2: observabilidade ativa, IP Groups criados, {{c.rcg.baselineNs.name}} e {{c.rcg.baselineEw.name}} funcionando, e as precedências de {{c.rcg.wlA.name}} e {{c.rcg.wlB.name}} já demonstradas.

Não rode o deploy da base depois deste exercício

Depois do Ex3, as policies {{c.names.polEw}} e {{c.names.polNs}} passam a herdar de {{c.names.polParent}}. Rodar o deploy da base de novo removeria o basePolicy das filhas. O ./scripts/deploy.sh recusa reexecutar quando {{c.names.rg}} já existe, salvo se você usar --force.

Fontes usadas neste exercício

As regras de herança, processamento por tipo e restrições de policy foram validadas na documentação oficial: hierarquia de policies, policy overview, rule processing e FAQ do Azure Firewall.

3.1 · Criar a policy pai

O que: crie {{c.names.polParent}} como policy Premium na mesma região das filhas, com o RCG {{c.rcg.corp.name}} e a collection {{c.rc.appCorp.name}}.

Por que: a policy pai precisa estar na mesma região das filhas para a herança funcionar, e o tier precisa ser compatível com o que as filhas usam. Como o lab usa Azure Firewall Premium e os exercícios seguintes dependem de recursos Premium, o pai também será Premium.

O RCG {{c.rcg.corp.name}} usa prioridade {{c.rcg.corp.priority}}, um número "pior" de propósito. Mesmo assim, por estar no pai, ele será avaliado antes dos RCGs das filhas do mesmo tipo.

Portal

  1. Crie a policy. Abra Azure Firewall Manager › Security › Azure Firewall Policies e clique em + Create Azure Firewall Policy. Na aba Basics, preencha:
    • Resource group: {{c.names.rg}}
    • Name: {{c.names.polParent}}
    • Region: a mesma das policies filhas
    • Policy tier: Premium
    • Parent policy: None (ela é o pai)
    Não use a aba Rules do assistente: ali as collections vão para grupos padrão, e o exercício precisa do grupo próprio {{c.rcg.corp.name}}. Clique em Review + create › Create e espere a implantação terminar.
  2. Crie o grupo. Abra Firewall Policies › {{c.names.polParent}} › Rules › Rule collections e clique em + Add › Rule collection group:
    • Name: {{c.rcg.corp.name}}
    • Priority: {{c.rcg.corp.priority}}
    Clique em Add e espere Succeeded.
  3. Crie a collection. Clique em Refresh, depois em + Add › Rule collection, e preencha o cabeçalho:
    • Name: {{c.rc.appCorp.name}}
    • Rule collection type: Application
    • Priority: {{c.rc.appCorp.priority}}
    • Rule collection action: Allow
    • Rule collection group: {{c.rcg.corp.name}}
    Na tabela Rules, preencha uma linha:
    • Name: {{c.rules.allowMicrosoftCorp}}
    • Source type: IP Group
    • Source: {{c.names.ipgSpokes}}
    • Protocol: Http:{{c.targets.httpPort}},Https:443
    • Destination Type: FQDN
    • Destination: {{c.targets.baselineFqdn}}
    Clique em Add e espere Succeeded.
  4. Clique em Refresh e confira {{c.rc.appCorp.name}} dentro de {{c.rcg.corp.name}} ({{c.rcg.corp.priority}}).
CLI 
LOCATION=$(az group show -n {{c.names.rg}} --query location -o tsv)
IPG_SPOKES_ID=$(az network ip-group show -g {{c.names.rg}} -n {{c.names.ipgSpokes}} --query id -o tsv)

az network firewall policy create \
  -g {{c.names.rg}} \
  -n {{c.names.polParent}} \
  -l "$LOCATION" \
  --sku Premium

az network firewall policy rule-collection-group create \
  -g {{c.names.rg}} \
  --policy-name {{c.names.polParent}} \
  -n {{c.rcg.corp.name}} \
  --priority {{c.rcg.corp.priority}}

az network firewall policy rule-collection-group collection add-filter-collection \
  -g {{c.names.rg}} \
  --policy-name {{c.names.polParent}} \
  --rule-collection-group-name {{c.rcg.corp.name}} \
  -n {{c.rc.appCorp.name}} \
  --collection-priority {{c.rc.appCorp.priority}} \
  --action Allow \
  --rule-type ApplicationRule

az network firewall policy rule-collection-group collection rule add \
  -g {{c.names.rg}} \
  --policy-name {{c.names.polParent}} \
  --rule-collection-group-name {{c.rcg.corp.name}} \
  --collection-name {{c.rc.appCorp.name}} \
  -n {{c.rules.allowMicrosoftCorp}} \
  --rule-type ApplicationRule \
  --source-ip-groups "$IPG_SPOKES_ID" \
  --protocols Http={{c.targets.httpPort}} Https=443 \
  --target-fqdns {{c.targets.baselineFqdn}}

Verifique: {{c.names.polParent}} existe, está como Premium e contém {{c.rcg.corp.name}} › {{c.rc.appCorp.name}} › {{c.rules.allowMicrosoftCorp}}.

3.2 · Re-parent das policies filhas

O que: conecte {{c.names.polEw}} e {{c.names.polNs}} ao pai {{c.names.polParent}}.

Por que: as duas policies já existem e estão associadas aos firewalls. Ao apontar cada uma para o pai, elas passam a herdar as regras de {{c.names.polParent}} sem perder as próprias. O Portal permite trocar o pai de uma policy existente. No CLI, o caminho usa --set basePolicy.id=<id>.

Portal

  1. Abra Azure Firewall Manager › Security › Azure Firewall Policies › {{c.names.polEw}}.
  2. Defina a Parent policy como {{c.names.polParent}} e salve.
  3. Faça o mesmo em {{c.names.polNs}}.

As duas policies são independentes: dá para fazer as duas ao mesmo tempo, em abas separadas, sem esperar uma terminar para começar a outra. Depois, espere as duas voltarem a Succeeded.

CLI 
PARENT_ID=$(az network firewall policy show \
  -g {{c.names.rg}} \
  -n {{c.names.polParent}} \
  --query id -o tsv)

for POLICY in {{c.names.polEw}} {{c.names.polNs}}; do
  az network firewall policy update \
    -g {{c.names.rg}} \
    -n "$POLICY" \
    --set basePolicy.id="$PARENT_ID"
done

for POLICY in {{c.names.polEw}} {{c.names.polNs}}; do
  az network firewall policy show \
    -g {{c.names.rg}} \
    -n "$POLICY" \
    --query "{policy:name,parent:basePolicy.id,state:provisioningState}" \
    -o table
done

Verifique: as duas filhas mostram {{c.names.polParent}} como Parent policy.

3.3 · Remover o allow duplicado da policy N-S

O que: remova {{c.rules.allowMicrosoft}} da filha {{c.names.polNs}}, porque {{c.rules.allowMicrosoftCorp}} no pai agora cobre o mesmo destino comum.

Por que: regra comum duplicada em pai e filha dificulta troubleshooting. Se {{c.rules.allowMicrosoft}} for a única regra da collection {{c.rc.appBaseline.name}}, remova a collection inteira para deixar a intenção clara.

Portal

  1. Abra Firewall Policies › {{c.names.polNs}} › Rules › Rule collections e localize o grupo {{c.rcg.baselineNs.name}} na lista.
  2. Abra a collection {{c.rc.appBaseline.name}}.
  3. Remova a regra {{c.rules.allowMicrosoft}}. Se ela for a única regra da collection, remova {{c.rc.appBaseline.name}} inteira.
  4. Clique em Save.
  5. Espere o provisioning voltar para Succeeded e aguarde mais 1–2 minutos para propagação.
CLI 
# O help local do az mostra --name como o nome da collection neste subcomando.
# Use este caminho quando {{c.rules.allowMicrosoft}} for a única regra de {{c.rc.appBaseline.name}}.
az network firewall policy rule-collection-group collection remove \
  -g {{c.names.rg}} \
  --policy-name {{c.names.polNs}} \
  --rule-collection-group-name {{c.rcg.baselineNs.name}} \
  --name {{c.rc.appBaseline.name}}

while [ "$(az network firewall policy show -g {{c.names.rg}} -n {{c.names.polNs}} --query provisioningState -o tsv)" != "Succeeded" ]; do
  echo "Aguardando propagação da policy..."
  sleep 30
done
sleep 120
az vm run-command invoke \
  -g {{c.names.rg}} \
  -n {{c.names.vmB}} \
  --command-id RunPowerShellScript \
  --scripts 'Invoke-WebRequest https://{{c.targets.allowedProbe}} -UseBasicParsing | Select-Object -ExpandProperty StatusCode' \
  --query "value[0].message" \
  -o tsv

Verifique: a VM-B continua acessando {{c.targets.allowedProbe}} com HTTP 200. A decisão deve vir do pai. A coluna Policy mostra {{c.names.polParent}}, e o RCG {{c.rcg.corp.name}} confirma que a regra veio do pai.

Teste na VM-B, pelo Bastion (PowerShell) ou pelo {{c.names.vmB}} › Operations › Run command › RunPowerShellScript:

Invoke-WebRequest https://{{c.targets.allowedProbe}} -UseBasicParsing

3.4 · Experimento: o Deny da filha ainda vence?

Previsão

O Deny de {{c.targets.learn}} para a VM-A, criado no Ex2 em {{c.rcg.wlA.name}} › {{c.rc.appWlA.name}}, continua valendo depois que o pai permite {{c.targets.baselineFqdn}}?

Portal

  1. Abra Virtual machines › {{c.names.vmA}} › Run command › RunPowerShellScript.
  2. Execute o teste para https://{{c.targets.learn}}.
  3. Depois abra {{c.names.law}} › Logs e rode a consulta do Ex2 ou a consulta ex3-heranca para ver qual RCG decidiu.
CLI 
az vm run-command invoke \
  -g {{c.names.rg}} \
  -n {{c.names.vmA}} \
  --command-id RunPowerShellScript \
  --scripts 'Invoke-WebRequest https://{{c.targets.learn}} -UseBasicParsing | Select-Object -ExpandProperty StatusCode' \
  --query "value[0].message" \
  -o tsv

Registre: o resultado do teste da VM-A e o RCG que aparece no log. Só então abra a resposta.

Ver resposta

Não. O acesso passa. O Allow amplo {{c.rules.allowMicrosoftCorp}} no pai é avaliado antes dos RCGs da filha e fura o Deny {{c.rules.denyLearn}} da filha.

Lição de design

No pai, coloque guardrails corporativos, principalmente Deny, e infraestrutura comum. Allows específicos de workload ficam nas filhas para evitar que um Allow central amplo neutralize exceções locais.

3.5 · Experimento: guardrail central para RDP E-W

Previsão

Abra uma sessão RDP da VM-A para a VM-B e deixe a sessão aberta. Depois crie no pai um Deny TCP {{c.targets.rdpPort}} entre spokes. O que acontece com a sessão já aberta, um novo RDP, o ping e a sessão Bastion → VM-A?

Portal

  1. Conecte na VM-A pelo Bastion.
  2. Dentro da VM-A, abra mstsc, conecte em {{c.network.vmBIp}} e deixe a sessão RDP aberta.
  3. Abra Firewall Policies › {{c.names.polParent}} › Rules › Rule collections.
  4. Clique em + Add › Rule collection: nome {{c.rc.netCorpGuardrail.name}}, tipo Network, prioridade {{c.rc.netCorpGuardrail.priority}}, ação Deny e grupo {{c.rcg.corp.name}}.
  5. Adicione a regra {{c.rules.denyRdpEw}}: protocolo TCP, porta {{c.targets.rdpPort}}, origem {{c.names.ipgSpokes}}, destino {{c.names.ipgSpokes}}.
  6. Salve, espere o provisioning voltar para Succeeded e aguarde mais 1–2 minutos.
CLI 
IPG_SPOKES_ID=$(az network ip-group show -g {{c.names.rg}} -n {{c.names.ipgSpokes}} --query id -o tsv)

az network firewall policy rule-collection-group collection add-filter-collection \
  -g {{c.names.rg}} \
  --policy-name {{c.names.polParent}} \
  --rule-collection-group-name {{c.rcg.corp.name}} \
  -n {{c.rc.netCorpGuardrail.name}} \
  --collection-priority {{c.rc.netCorpGuardrail.priority}} \
  --action Deny \
  --rule-type NetworkRule

az network firewall policy rule-collection-group collection rule add \
  -g {{c.names.rg}} \
  --policy-name {{c.names.polParent}} \
  --rule-collection-group-name {{c.rcg.corp.name}} \
  --collection-name {{c.rc.netCorpGuardrail.name}} \
  -n {{c.rules.denyRdpEw}} \
  --rule-type NetworkRule \
  --source-ip-groups "$IPG_SPOKES_ID" \
  --destination-ip-groups "$IPG_SPOKES_ID" \
  --ip-protocols TCP \
  --destination-ports {{c.targets.rdpPort}}

while [ "$(az network firewall policy show -g {{c.names.rg}} -n {{c.names.polParent}} --query provisioningState -o tsv)" != "Succeeded" ]; do
  echo "Aguardando propagação da policy pai..."
  sleep 30
done
sleep 120
az vm run-command invoke \
  -g {{c.names.rg}} \
  -n {{c.names.vmA}} \
  --command-id RunPowerShellScript \
  --scripts 'Test-NetConnection {{c.network.vmBIp}} -Port {{c.targets.rdpPort}}; Test-Connection {{c.network.vmBIp}} -Count 4' \
  --query "value[0].message" \
  -o tsv

Registre: o que aconteceu com a sessão RDP aberta, com um novo RDP, com o ping e com a sessão Bastion. Só então abra a resposta.

Ver resposta

A sessão RDP aberta cai: a documentação de processamento de regras afirma que, quando uma regra passa a negar um tráfego antes permitido, o Azure Firewall derruba as sessões existentes relevantes. Um novo RDP A→B falha, mas o ping continua funcionando porque o guardrail bloqueia apenas TCP {{c.targets.rdpPort}}.

A sessão Bastion → VM-A não cai, porque esse caminho usa o peering entre {{c.names.vnetNs}} e {{c.names.vnetA}}, sem passar pelo firewall. O RCG {{c.rcg.corp.name}} do pai, mesmo com prioridade {{c.rcg.corp.priority}}, vence o {{c.rcg.baselineEw.name}} da filha com prioridade {{c.rcg.baselineEw.priority}}, porque pai é processado antes da filha.

3.6 · Auditar as mudanças com change tracking

O que: use o Azure Resource Graph para listar o que mudou nas rule collection groups durante este exercício, com valor anterior e novo.

Por que: numa hierarquia, a pergunta "quem mexeu na regra e o que era antes?" aparece logo depois de um incidente. O change tracking das rule collection groups responde o que mudou, sem você ter guardado um "antes"; o Activity Log responde quem mudou. O change tracking está em preview.

Portal

  1. Pesquise e abra Resource Graph Explorer.
  2. Cole a consulta abaixo e clique em Run query. Ela roda no Resource Graph, não no Log Analytics.
  3. Procure as mudanças dos passos 3.3 e 3.5: a remoção de {{c.rules.allowMicrosoft}} em {{c.rcg.baselineNs.name}} de {{c.names.polNs}} e o guardrail {{c.rules.denyRdpEw}} em {{c.rcg.corp.name}} de {{c.names.polParent}}.
  4. Quem fez a mudança? O change tracking não traz o usuário: nessa tabela, changedBy vem como Unspecified. Quem responde é o Activity Log. Rode o bloco abaixo no Cloud Shell e case cada linha com uma mudança do change tracking pelo horário: a coluna quem mostra o usuário ou a identidade que fez a alteração. O Activity Log registra quando a operação terminou, então o horário dele costuma vir alguns minutos depois do Timestamp do change tracking.
az monitor activity-log list -g {{c.names.rg}} --offset 1d \
  --query "[?contains(operationName.value, 'ruleCollectionGroups') && status.value=='Succeeded'].{quando:eventTimestamp, quem:caller, operacao:operationName.value}" -o table
CLI 
az extension add --name resource-graph --upgrade
az graph query -q "$(grep -v '^//' queries/ex3-change-tracking.kql)" --first 100 -o table
{{kql:ex3-change-tracking}}

Verifique: aparecem linhas de {{c.names.polNs}}/{{c.rcg.baselineNs.name}} e de {{c.names.polParent}}/{{c.rcg.corp.name}}, com ChangeType e, em PreviousValue/NewValue, a regra que saiu e o guardrail que entrou. Se ainda não aparecer nada, espere alguns minutos e rode de novo: o registro da mudança não é instantâneo. No Activity Log, os mesmos horários aparecem com o seu próprio usuário.

O C3 verifica: {{c.names.polParent}} existe, as duas filhas apontam para o pai e {{c.rules.allowMicrosoft}} saiu da filha N-S. O guardrail do 3.5 não entra no checkpoint: o experimento é conferido pelo resultado do teste e pela KQL do próprio passo.

O que você aprendeu

  • Policy pai é mecanismo de governança central: ela deve impor guardrails e padrões comuns.
  • Allows amplos no pai podem furar Denies específicos das filhas; use-os com cuidado.
  • A prioridade numérica não muda a regra principal: pai antes da filha, depois DNAT → Network → Application.
  • Mudanças de Allow para Deny podem derrubar sessões existentes que passem pelo Azure Firewall.
